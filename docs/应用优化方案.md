# U-Brain 应用优化方案与执行计划

> 日期：2026-11-17（同日按代码与产物核查后修订）  
> 目标：在不大改产品边界的前提下，把安装体积、冷/热启动、常驻页面的后台开销、搜索索引稳定性推到可预期的高水准。  
> 依据：`dist/app.noindex` 与 `apps/web/dist` 实测、运行中 daemon 的进程采样、`docs/TODO.md` 遗留项（F24 搜索索引）、`docs/知识库体验优化方案.md` 未收尾项。  
> 状态：执行中；每完成一项更新本文「实施记录」，涉及 TODO 的同步 `docs/TODO.md`。

## 2. 原则

1. **产品边界不动**：KeepAlive 保留主导航状态；T3/DSH 双轨保留，体积优化先砍重复和用不到的载荷，不砍能力。
2. **先测后砍**：每项改动给出构建产物或计时对比。
3. **与知识库方案分工**：知识库编辑器性能见 `知识库体验优化方案.md`；本方案覆盖打包、壳层、常驻页面、daemon 索引。
4. **最小提交粒度**：按任务编号分批提交，每批跑 `bun run typecheck` 和相关测试。
5. **新依赖先确认**：`@tanstack/react-virtual`、bundle 可视化插件等需要征得同意后再引入。

## 3. 问题清单与做法（按收益排序）

### P1 DSH 运行时里重复的 zod（−250 MB）

- **现象**：DSH 的 51 个 `@deepseek-ai/*` 包把 zod 锁死在 `4.4.3`，而顶层被 MCP SDK 等提升成 `4.6.7`，npm 只好给每个包各装一份嵌套副本，每份 5 MB。`scripts/build-dsh.ts` 只按包名整包删除，不去重。
- **不能用符号链接**：Tauri 打包资源时会把链接展开成实体文件（`dist/daemon` 里有链接，`.app` 里一个都没有），省不下体积。
- **做法**：构建时把重复副本提升到 `@deepseek-ai/node_modules/zod`，删掉各包里的嵌套副本。Node 的 CJS 和 ESM 解析都会先查 `@scope/node_modules`，再查顶层 `node_modules`。
- **安全条件**：提升后，原来解析到顶层 zod 的同 scope 包（4 个，声明 `^4.4.3`）会改用 4.4.3。脚本要逐个检查这些包声明的版本范围，任何一个不满足就放弃这次提升并打印原因。
- **验收**：`dsh` 目录 ≤ 330 MB；同 scope 每个声明 zod 的包都能解析到满足其范围的版本；DSH 能启动，指挥台能开会话。
- **顺带可裁**：`@img/sharp-wasm32`（8.9 MB，macOS 用的是原生 sharp）。文档预览的 pdf、excel 包（约 13 MB）要先确认 DSH 是否会加载，再决定是否裁掉。

### P2 常驻页面切走后仍在空转

- **现象**：KeepAlive 只给切走的页面设 `hidden`（`apps/web/src/app.tsx:110`），轮询只看 `document.visibilityState`，窗口开着就一直跑：
  - `pages/tasks.tsx:73`：每 5 s 拉待办
  - `pages/deck-tty7-sessions.ts:86`：每 5 s 拉 tty7 会话
  - `pages/dsh-deck.tsx:120`：每 3 s 确认 DSH 地址；启动中是每 1 s（`:90`）
  - `pages/knowledge.tsx:361`：每 1 s 的检查定时器
- 话题页的「进行中」和「历史」两个实例都常驻。每个 topics 事件都会拉一次全量话题（`daemon-context.tsx:191`），两个实例各自重算 `map`、`filter`、`visibleTopics`，没有 `useMemo`；话题量在 1000 条左右。
- **做法**：
  1. KeepAlive 为每个页面提供 `PageActiveContext`，新增 `usePageActive()`。
  2. 上面这些轮询改成「页面激活且窗口可见」时才跑；重新激活时立即拉一次。
  3. 话题页的派生数据加 `useMemo`。不激活的实例不接收列表更新也可以，激活时再算。
- **验收**：停在非指挥台页面 1 分钟，网络面板里只剩事件流；话题页切换无可感知卡顿。

### P3 首包拆分与懒加载

- **现象**：所有页面都同步 import（`app.tsx:6-15`）。xterm 约 470 KB、KaTeX 约 300 KB、Prism 全部进了首包。托盘面板（`/panel`）和提醒弹窗（`/reminder-popup`）是独立窗口，也加载这 1.6 MB 全量包，拆包对它们的冷启动收益最大。
- **做法**：
  1. `/search`、`/settings`、`/_design`、`/panel`、`/reminder-popup` 改成 `React.lazy`。
  2. KeepAlive 页面也改成 lazy：首次进入才加载，之后常驻，不影响保留状态。知识库页（`knowledge.tsx`，2850 行）连带 KaTeX、Prism 一起拆出去。
  3. tty7 终端（`deck-tty7-terminal.tsx`）用 `import()` 加载 xterm。
  4. 需要显式分组时用 rolldown 的 `build.rolldownOptions.output.codeSplitting`。Vite 8 底层是 rolldown 1.2，`manualChunks` 已标为废弃。
- **验收**：面板和提醒窗口首包不含 xterm、KaTeX；主窗口首包 ≤ 800 KB。

### P4 F24 搜索索引在 410 后全量重建

- **根因已确认**：`changes.list` 返回 410 后，`google-drive.ts:706` 带着 `reset: true` 从头列出；`search-service.ts:606` 随即清空 `search_vectors`、`search_chunks`、`search_chunks_fts` 三张表，嵌入全部重算。
- **做法（分两步）**：
  1. **按内容复用向量**：`search_chunks` 已有 `content_sha256`。reset 时不再先清空，而是记下旧的 `(chunk 内容哈希 → 向量)`；重新切块后哈希相同就直接复用向量，只对新增或变更的内容调用嵌入。最后删掉这轮没再出现的 `drive_file_id`。FTS 行照常重写，成本很低。
  2. **进度可见**：`StatusResponse.searchIndex = { phase: "idle" | "rebuilding", processed, total, startedAt }`，状态页显示。重建期间搜索照常走 FTS。
- **验收**：用 3k 文档的库模拟 410，重建 ≤ 5 min，嵌入调用次数 ≈ 变更 chunk 数；有单测覆盖「内容不变不重嵌」「删除的文件被清掉」。
- 原方案「按文档 md5 对账」降为备选：Drive 文件 md5 不变不代表切块规则没变，按 chunk 哈希复用更稳。

## 5. 风险与回滚

| 风险 | 缓解 |
|------|------|
| zod 提升后某个 DSH 包用到 4.6 才有的 API | 脚本按声明范围校验；验收时实际启动 DSH 并开会话；出问题 revert 构建脚本即可，不涉及数据 |
| 懒加载首进白闪 | `Suspense` 用页面同款骨架；KeepAlive 页面只在第一次进入时加载 |
| 暂停轮询导致回到页面看到旧数据 | 重新激活时立即拉一次，并保留事件流驱动的刷新 |
| 向量复用把旧模型的向量混进新索引 | 复用条件加上模型名和维度；模型变化时走全量 |
| F24 与 Drive 竞态 | 沿用既有「自上传 md5 跳过」语义，写入方仍只有一个 |
