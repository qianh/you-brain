# 跨设备派活：协议与数据结构

> 配套 [跨设备派活-实施计划.md](./跨设备派活-实施计划.md) 的 M2～M5。中转（`services/telegram-relay`）、协议包（`packages/protocol/src/dispatch.ts`）、目标端执行器（`packages/core/src/dispatch/`）、设备端客户端（`packages/core/src/deck/telegram/relay.ts`）都以本文为准；改协议先改本文。

## 1. 身份与入网（M2）

- 每台设备首次入网时本机生成 **Ed25519** 密钥对，私钥存 `SecretStore`（钥匙串），公钥以 base64url（SPKI DER）上报。
- 中转设备表 `{deviceId, name, tokenHash, publicKey, createdAt, revokedAt?}`；令牌 `ubd_<32 字节 base64url>`，中转只存 `sha256` 的 hex。
- 邀请码：8 位（字母表同绑定码），10 分钟有效、一次性。错误兑换累计 5 次，作废当前全部未用邀请码。
- 管理端点（只给 VPS 本机用，Caddy 对外 404；中转收到带 `X-Forwarded-For` 的请求一律 404；Bearer = `RELAY_KEY`）：
  - `POST /admin/invite` → `{code, expiresAt}`
  - `POST /admin/revoke` body `{deviceId}` → 立即断开该设备的连接并拒绝重连
  - `GET /admin/devices` → 设备表（不含 tokenHash）
  - 命令行 `bun src/admin.ts invite|revoke <deviceId>|devices` 是对上面端点的封装，读 `RELAY_KEY` 与 `RELAY_ADMIN_URL`（默认 `http://127.0.0.1:8787`）。
- 兑换：`POST /enroll` body `{code, deviceId, name, publicKey}` → `{token}`（令牌只在这一次返回）。同一个 `deviceId` 已存在且未吊销时拒绝（要换密钥必须先吊销）。
- 鉴权：`/connect` 的 `Authorization: Bearer <设备令牌>`，查询参数 `device` 必须与令牌对应的设备一致。过渡期（环境变量 `RELAY_ACCEPT_LEGACY_KEY`，默认 `true`）仍接受 `RELAY_KEY`，用旧密钥连上的设备**不能**收发 `cmd` / `event` 帧（返回错误「请先入网」）。`/check` 同样接受两种凭据。
- 自动入网（同一个 Google Drive 账号）：已入网设备 `POST /invite`（`Authorization: Bearer <设备令牌>`，每台设备每小时最多 30 次，旧共享密钥不行）→ `{code, expiresAt}`；设备把 `{url, code, expiresAt, issuedBy}` 写进云盘 `you-brain/relay/invite.json`（`DRIVE_PATHS.relayInvite`），心跳（5 分钟）里剩余不到 6 分钟就换新的。没入网的设备启动和心跳时读这份文件，邀请码没过期且没失败过就按普通入网兑换。云盘账号是信任边界：能读这个文件夹的人能让新设备入网，所以邀请码仍是 10 分钟、一次性；入网后的设备默认**不接受**派活（目标端策略不变）。正在用自己 Bot Token 直连的设备不自动入网。
- 审计：中转追加写 `<dataDir>/audit.jsonl`，每行 `{ts, from, to, kind, outcome}`，**不含正文与参数**；入网、吊销、拒绝（未入网/离线/限速/过大/重放）也记。

## 2. 帧（JSON 文本，在现有 `req` / `res` / `state` / `message` 之外新增）

`protocolVersion = 1`。收到不认识的 `t` 一律忽略（旧客户端已是如此）。

设备 → 中转：

```jsonc
{"t":"req","id":"7","op":"hello","protocolVersion":1,"version":"app 版本","dispatch":{"enabled":true,"t3":{"ready":true,"version":"0.1.9"},"projects":[{"id":"p1","name":"you-brain"}],"maxMode":"auto"}}
{"t":"req","id":"8","op":"cmd","cmdId":"c-…","to":"<目标 deviceId>","cmd":{"kind":"t3.start","args":{…}},"ts":1760000000000,"nonce":"<16 字节 base64url>","sig":"<base64url>"}
{"t":"req","id":"9","op":"result","cmdId":"c-…","ok":true,"result":{…}}      // 或 "ok":false,"error":"…"
{"t":"req","id":"10","op":"event","to":"<发起方 deviceId>","dispatchId":"d-…","kind":"thread.status","data":{…}}
```

中转 → 设备：

```jsonc
{"t":"res","id":"8","ok":true,"result":{"accepted":true}}     // 对 cmd 的受理；目标离线/限速/过大/重放时 ok:false 立即失败
{"t":"cmd","cmdId":"c-…","from":"<发起方 deviceId>","to":"<目标 deviceId>","cmd":{…},"ts":…,"nonce":"…","sig":"…"}
{"t":"cmdres","cmdId":"c-…","from":"<目标 deviceId>","ok":true,"result":{…}}   // 或 ok:false,error
{"t":"event","from":"<目标 deviceId>","dispatchId":"d-…","kind":"thread.status","data":{…}}
{"t":"state", …现有字段, "devices":[{"id","name","online","enrolled":true,"publicKey":"…","dispatch":{…hello 里的 dispatch…}}]}
```

- `state.devices[].dispatch` 来自该设备最近一次 `hello`（离线设备保留最后一次并带 `online:false`）；`publicKey` 只对已入网设备给出，用于目标设备本机确认发送方。
- 设备每次（重）连上后发一次 `hello`，策略变化（开关、白名单、T3 就绪与否）时再发一次。

## 3. 规则（中转强制执行）

- 发起方必须是已入网设备；`cmd.from` 由中转按连接身份填，不信帧里的自述。
- 目标不在线：立即回 `res ok:false error:"目标设备不在线"`，**不排队**。
- 指令 TTL 60 秒：`|now - ts| > 60s` 拒绝；`(from, nonce)` 在 TTL 窗口内出现过拒绝（重放）。
- 单条 `cmd` 帧 ≤ 64 KB；`result` 帧 ≤ 256 KB（超出：对发起方回 `cmdres ok:false error:"结果过大"`）。
- 限速：每台发起设备 30 条 `cmd` / 分钟；超出回 `res ok:false`。
- 待结果表（内存）：`cmdId → {from, to, expiresAt}`，`expiresAt = ts + 5 分钟`；`result` 必须来自 `to` 且 `cmdId` 存在、只接受一次。超时无结果：5 分钟时对发起方发 `cmdres ok:false error:"目标设备没有返回结果"`。
- `event` 的 `to` 不在线则丢弃（不排队）；同一目标限速 120 条/分钟。

## 4. 签名（目标端验证，不信中转转来的公钥）

规范串（`\n` 连接，UTF-8）：

```
u-brain-cmd/1
<cmdId>
<from deviceId>
<to deviceId>
<ts>
<nonce>
<sha256 hex of canonicalJson(cmd)>
```

`canonicalJson`：对象键递归按字典序排序、无空白的 JSON。签名 `Ed25519(私钥, 规范串)`，base64url。实现放 `packages/protocol/src/dispatch.ts`（`canonicalJson`、`signingString`、`signCommand`、`verifyCommand`）。

目标端验签要求帧里的 `to` 等于本机 `deviceId`，所以中转下发 `cmd` 时必须原样带 `to`。重试同一条指令：**换 `nonce` 并重新签名**，`cmdId` 保持不变（命中幂等，直接返回已有结果）；原帧在 60 秒内重发会被当成重放拒绝。`t3.start` 失败后同一 `cmdId` 会一直返回那次错误，要重试需换 `cmdId`、沿用同一个 `dispatchId`。

## 5. 指令（`cmd.kind` 与 `args` / 结果）

第一期只有 T3；目标不认识的 `kind` 返回 `error:"不支持的指令：<kind>"`。

| kind | args | 结果 |
|---|---|---|
| `t3.projects` | `{}` | `{projects:[{id,name}]}`，仅白名单内项目 |
| `t3.start` | `{projectId, title, prompt, mode?, dispatchId}` | `{threadId, threadUrl, mode, capped}`；`mode` 取值 `auto-accept-edits` / `auto` / `full-access`，缺省 `auto`；`mode` 是**实际生效值**，`capped` 表示被本机上限降级过 |
| `t3.followup` | `{threadId, prompt, requestId}` | `{}`，仅限账本里由派活创建的会话 |
| `t3.read` | `{threadId}` | `{state:"planning"\|"running"\|"ready"\|"failed", summary, error?, link}`，仅限账本里的会话 |
| `t3.threads` | `{}` | `{threads:[{threadId,title,status,link,dispatchId}]}`，仅账本里的会话 |

事件 `kind`：`thread.status`，`data:{threadId,status,previous,title,link}`（只对账本里的会话发；复用 `t3/watch.ts` 的 15 秒监视）。

## 6. 目标端本机策略与账本

`<dataDir>/dispatch/policy.json`（0600，原子写）：

```jsonc
{"enabled":false,"notify":true,"maxMode":"auto",
 "allowedSenders":[{"deviceId":"…","name":"Mac A","publicKey":"…"}],
 "allowedProjects":["<T3 项目 id>"]}
```

判定顺序（任一不满足即拒绝并记审计）：`enabled` → 签名有效 → 发送方在 `allowedSenders` 且公钥与本机记录一致 → TTL / nonce → `kind` 已知 → 项目在 `allowedProjects` → 权限 = min(请求值, `maxMode`)。

账本 `<dataDir>/dispatch/ledger.json`：`{[dispatchId]:{threadId, from, projectId, title, createdAt}}` 与 `{[cmdId]:结果}`（去重用，保留 7 天、最多 1000 条）。同一 `cmdId` 或 `dispatchId` 重放直接返回已有结果，不新建会话。审计 `<dataDir>/dispatch/audit.jsonl`（不含 prompt 正文）。

## 7. 发起端

- `<dataDir>/dispatch/outbox.json`：`{[dispatchId]:{to, deviceName, projectId, title, mode, cmdId, threadId?, status, createdAt, updatedAt, lastSummary?}}`，保留 30 天。
- daemon HTTP：`GET /api/dispatch/devices`、`POST /api/dispatch/send`（`{to, kind, args}`，等待目标结果，超时 45 秒）、`GET /api/dispatch/outbox`、`GET /api/dispatch/outbox/:dispatchId`。
- MCP 工具：`list_devices`、`dispatch_to_device`、`get_dispatch_result`、`send_to_dispatch`。
- `event` 到达后：更新 outbox；状态变为「做完一轮 / 等你处理 / 失败」时按 Telegram 桥现有规则推送，含最后一条回答摘要。

## 8. 手机回复的路由（不引用也能回对会话）

- 引用某条推送回复：中转按 `routes` 表（`[messageId, deviceId, preview, at]`）直接转给推送它的设备，行为不变。
- 不引用：配了 `RELAY_ROUTER_DEVICE` 且该设备在线、且 6 小时内有推送时，中转不再按「最近设备」转，而是向路由设备发 `{"t":"route","message":{…},"candidates":[{"id","deviceId","deviceName","preview","at"}]}`（最多 8 条，新的在前）。否则回退「最近设备」（2 小时内）。
- 路由设备判断后发 `{"t":"req","op":"forward","message":{…},"target":<推送 messageId>}`；中转只接受路由设备的 `forward`，校验聊天 id 与目标推送仍在表里，再把消息改成「回复了 target」转给对应设备，并把该设备记为最近设备。目标设备不在线或推送已过期时返回错误。
- 路由设备的判断：只有一个候选直接转；多个候选交给 daemon 的 LLM（45 秒超时），只有内容明确指向某一条才选，「收到」「好」这类通用的话、超时、出错都按「拿不准」处理；拿不准就在 Telegram 里发带序号的清单，用户回序号（「2」「选2」「第 2 个」），10 分钟内有效，转发的是原来那句话。
- 派活结果推送（发起端 daemon 推的）也登记为可回复的推送，回复会作为 `t3.followup` 发回派出的会话。
