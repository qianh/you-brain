## 2. 当前数字分身内容的问题

### 2.1 【P1】`projects` 层同项目异名分裂，且跨文件口径正反打架

当前 `projects.md` 按 `## 项目名` 前缀聚合拆出 48 个项目文件，同一产品或同一代码仓库因对话叫法不同被拆成多个互不相通的文件，且近半数缺失 `> repos:` 映射：

1. **本项目自身裂成 5 份文件**：
   - `projects/you-brain.md`（8,597 B，带 `> repos: you-brain`，9 个子节）
   - `projects/u-brain.md`（无 `repos`，存放开发 TODO 自动领取与人工核对合并规则）
   - `projects/指挥台.md`（3,014 B，无 `repos`）
   - `projects/t3-code.md`（无 `repos`）
   - `projects/终端与网关.md`（无 `repos`）
   - **召回盲区**：在 `you-brain` 仓库内工作时，`lookupProjectPortrait`（`packages/core/src/portrait/projects-split.ts:196-200`）命中第一优先级 `repos: you-brain` 后立即返回 `you-brain.md`，**完全漏掉** `u-brain.md`、`指挥台.md`、`终端与网关.md` 中的规则。
2. **同一业务域裂成多份并出现正反冲突**：
   - 例如某业务系统 A 的同一功能决策分散在 4 个独立项目组中（其中 2 个无 `repos`、2 个挂在同一后端仓库上），两组对同一界面布局给出了左右相反的约定；两份文件各自维护，互不知情。
   - 某业务系统 B 的决策分散在 3 个都映射到同一仓库的项目组中，同一数据约束与接口例外在多处重复抄写。
3. **主力大项目缺失仓库映射**：多个 8 KB～10 KB 级的核心项目组未维护 `> repos:`，在对应代码仓库下按目录名查询 `get_portrait(variant="projects", project="<repo>")` 时无法直接命中。

### 2.2 【P1】`projects` 旧口径未淘汰，且把单次需求/缺陷修复记成永久口径

1. **已被推翻的旧设计与现行实现并存（甚至同文件自相矛盾）**：
   - `projects/you-brain.md` 前文保留着早期「不采用 hook，以及逐个工具写规则或做配置的方案」「每天 10:00 把数字分身资产拉到各设备」，后文又写「通过托管块在各 CLI 规则文件中直接内联编码分身正文」。
   - `projects/指挥台.md` 与 `projects/t3-code.md` 仍写着「指挥台中的 T3 保持原样，不做额外处理」「完成提醒点击不跳到具体内容」「接入部分去掉 MCP 和 skill 的接入」，均与 `CONTEXT.md` 已落地的 T3 转发脚本注入、置顶弹框一键跳转整屏终端、T3 MCP 接入直接冲突。
2. **一次性工单与 UI 细节挤爆项目预算**：
   - 6 个项目组突破 `projectGroup = 8,192 B`（最高达 12,398 B）。抽查可见大量「某页面补上两个字段」「空行不要出现占位提示」「点击新项时清除之前的 focus」这类早已在代码里修完的单次交互细节被当成长期项目决定保留，稀释了真正需要跨会话遵守的架构边界与业务不变量。

### 2.3 【P2】`full.md` 与 `coding.md` 存在跨层语义重复与边界模糊

1. **6 处同义工程规则在 `full` 与 `coding` 重复占位**：
   `twinCrossLayerProblems`（`packages/core/src/consolidate/twin-standard.ts:144-159`）仅按字符二元组 Jaccard 相似度 `>= 0.55` 拦截字面复读，未能拦住以下换了措辞的同义规则（违反「已在 `coding` 的通用工程规范不在 `full` 重复」）：
   - **只读提问 vs 授权执行**：`full.md` 第 4 节前两条 vs `coding.md`「问≠做，行动请求=授权」
   - **守范围与保护已有改动**：`full.md` 第 3 节第 5 条 vs `coding.md`「保护用户修改」「最小变更」
   - **单层验证不跨层外推**：`full.md` 第 4 节第 7 条 vs `coding.md`「成功不可跨层外推」
   - **默认中文与禁套话**：`full.md` 第 8 节第 1 条、第 9 节末条 vs `coding.md`「沟通表达」
   - **敏感信息零暴露**：`full.md` 第 9 节第 4 条 vs `coding.md`「敏感信息零暴露」
   - **子代理上下文交接**：`full.md` 第 8 节第 11 条 vs `coding.md`「子代理边界」「分工与整合」
2. **`full` 内部存在未标清触发条件的表面冲突**：
   - `full.md` 第 4 节同时写有「需要他动手或确认的事**一次问齐**」与「需要他做选择时，**一问一答**」。虽然提示词契约（`packages/core/src/consolidate/prompt.ts:150`）明确要求区分「方向已定执行前一次问齐依赖」与「方案未对齐 grill 阶段一问一答」，但当前 `full.md` 正文把前置条件省掉了。
3. **本机特定 Skill 名混入人格层**：
   - `full.md` 第 8 节末条写入了特定本机 skill 名称（只在装有该 skill 的环境下成立），不属于跨平台通用人格。
4. **`coding.md` 条数已达硬上限（26/26）**：
   - 后续批准新提案时，若用 `add` 而非 `replace`，会直接触发 `CODING_TOTAL_LIMIT = 26`（`twin-standard.ts:30`）阻断报错。
5. **三层头部版本号观感不一致**：
   - 因未变动的层保持原文件字节不变，本机同时呈现 `full v4.8.0`、`coding v4.6.0`、`projects v4.13.0`，阅读时难以直观判断三层是否处于同一轮同步状态。

## 3. 沉淀、评测与分发方案的机制问题

### 3.1 【P1】项目抽取与局部合并机制天然制造「项目孤岛」，且无归并回路

1. **抽取侧缺失会话目录与已有项目别名上下文**：
   - `readTwinSessions`（`packages/core/src/consolidate/portrait-drive.ts:280-284`）只给抽取模型传了 `session.title` 与用户发言，丢掉了采集阶段已知的会话工作目录（仓库名）和已归属话题。
   - `portraitStep`（`packages/core/src/consolidate/portrait.ts:212`、`1329-1336`）只把 `projectNames(before.projects)` 纯名称数组传给抽取器，**未传各项目的 `> repos:` 列表与子主题标题**。模型看到用户在聊「指挥台」或「U-Brain」时，不知道它们从属 `you-brain`，直接产出新 `project` 名。
2. **合并侧局部切片导致跨组失明**：
   - `selectTargetProjectSections`（`packages/core/src/consolidate/portrait.ts:1074-1101`）只把精确或子串命中 `claim.project` / `claim.repo` 的现有项目组送进 `buildTwinProjectMergePrompt`。
   - 一旦抽出新名字 `U-Brain`，`targetProjectsText` 为空（提示词显示 `（新建项目小节）`），合并模型根本看不见已存在的 `## you-brain`，只能新建孤岛；后续即使修改 `you-brain`，也看不见 `指挥台` 里残留的冲突旧口径。
3. **缺少项目组归并机制**：
   - 话题册有 `merge_suggestions` 步骤定期识别同义话题，而 `projects.md` 没有任何同义项目检测与合并通道，孤岛一旦生成便永久留存。

### 3.2 【P1】只喂「用户单侧发言」+ `project` 层准入门槛过低

1. **剥离助手上下文导致指代丢失与性质误判**：
   - `readTwinSessions`（`portrait-drive.ts:283`）只保留 `turn.role === "user"`。用户在对话里说「按方案 A」「第二个留着，第一个删掉」时，缺少前一条助手回复的问题锚点，抽取器要么猜错、要么丢弃；而用户发出单次任务指令（如「列表加一列执行人」）时，也因看不到这只是常规开发任务而被抽成规则。
2. **`project` 层 `high` 置信度门槛过松**：
   - `CLAIMS_FROM_SESSIONS`（`packages/core/src/consolidate/prompt.ts:185-186`）对 `persona` / `coding` 要求出现「以后都 / 一律 / 必须」才标 `high`，但对 `project` 规定「用户明确拍板锁定该项目口径或纠正该项目做法标 `high`」。
   - 在日常编码会话中，任何具体功能指令都符合「拍板做法」，于是单次 UI 调整、字段增补直接以 `high` 写入 `projects.md`，变成需求流水账。

### 3.3 【P1】`projects` 超预算自愈闭环失效

当项目组总长超过 `TWIN_BUDGET.projectGroup = 8,192 B` 时，现有的自动压缩路径存在三处断点：

1. **字节明细在混合变更时丢失**：`buildTwinFixPrompt`（`packages/core/src/consolidate/prompt.ts:407-409`）仅在 `input.docs.full.trim() === "" && input.docs.coding.trim() === ""` 时才输出 `sectionSizes("projects", ...)`。只要当天同时改动了 `full`，修复模型就拿不到 `projects` 各节字节数。
2. **小节告警文案与压缩目标冲突**：项目组超限告警（`packages/core/src/consolidate/twin.ts:452`）要求删除已被推翻的旧口径，`TWIN_FIX_SYSTEM_PROMPT`（`prompt.ts:388-392`）也允许删掉最少触发的细则；但同轮出现的小节超限告警（`twin.ts:435`）写着「只合并同义表述……不删仍成立的规则」。两条告警同时出现时指令互相抵消，而单次历史细则彼此并不矛盾、都“仍成立”，模型倾向于只拆小节不删内容，项目组总长压不下来。
3. **Advisory 修复失败静默放行**：`finishTwin`（`packages/core/src/consolidate/portrait.ts:1215-1247`）对无阻断项的告警修复设 90 秒限时，未压下来或超时只记一条 warning 便把超限原文照常写入，导致 6 个大项目长期超标。

### 3.4 【P1】保真评测（`portraitEvalStep`）失真与信号漏传

1. **出题器把「抹去专名的单项目功能设计」当通用题考常驻层**：
   - 本机待审题 `p12`～`p24` 中，超过半数是具体业务或产品交互细节（如「知识库挂本地文件并重打包」「通知里的报告链接用系统浏览器打开」「多设备共用一个聊天机器人」「配置已有字段就跳过外部查询并回填历史」），只是抹去了具体平台与工具名。
   - 评测答题时模型只读 `full + coding`（`portrait.ts:548`），不可能凭空猜中单项目的具体产品方案；若将此类题审核入库，不仅测不出人格保真度，还会反向诱导把项目细节塞进常驻层。
2. **审核入口过深导致计分题量过小**：
   - 顶栏精简后，待审评测题与编码提案仅挂在「设置 → 数字分身 → 右侧折叠栏」（`apps/web/src/pages/portrait/side-panel.tsx:99-106`）或 CLI 命令中。待审题积压 13 道无人处理，正式题库长期停留在 7 道（单题波动即占 14.3%）。
3. **留出集的隔离依赖「补跑不读未来会话」**：
   - `twinBefore`（`portrait-drive.ts:138-145`）取 `day` 当天或之后的首个备份，找不到时回退读当前分身。由于所有分身写入都经 `save()` 先写备份（`portrait-drive.ts:85`）且备份从不清理，「找不到」即说明该层自 `day` 起未变，回退结果正确，**本身不构成穿越**；仅在 Drive 被外部手改或备份被手动删除时失真（P3 观察项）。
   - 真正的隔离缺口在 3.5.1：补跑某天时会提前消费之后的会话并合入分身，使该天之后的备份已含「未来」信息，留出题因此可能被分身提前学到。修复 3.5.1 即可恢复留出隔离。
4. **评测全链路未透传 `AbortSignal`**：
   - `evaluateTwin`（`portrait.ts:548-550`、`574`）调 `scoreProbes` → `scoreRound`（`portrait.ts:705-730`）时漏传 `signal`。一次周评测最多 4 组 × 3 轮 × 2 次 = 24 次模型调用，daemon 停机、换盘或步骤预算超时（`STEP_BUDGET_MS`）时无法中止在途请求。

### 3.5 【P2】增量状态管理与多日补跑的时间窗口漏洞

1. **多日补跑时 `readTwinSessions` 缺少日期上界（「未来会话穿越」）**：
   - `readTwinSessions`（`portrait-drive.ts:249-263`）只按 `sessionDay >= day - 1`（及近 7 天未读）过滤，**未限制 `sessionDay <= day`**。当按日补跑过去某天（如 `11-13`）时，会把 `11-14` 至今天的会话提前拉出抽取主张，并打上 `day: "2026-11-13"` 落盘到 `claims/2026-11-13.jsonl`。
2. **`pending.jsonl` 低置信主张升格后不剔除**：
   - `portraitStep`（`portrait.ts:260`、`272`、`400`）在低置信主张跨天复现触发合并后，仍将 `[...earlierLow, ...low]` 写回 `claims/pending.jsonl`（按 `PENDING_KEEP_DAYS = 60` 过期）。已被采纳合入分身的低置信主张不会退役，在过期前会反复作为「待定主张」送进合并与提案提示词，挤占 `TWIN_PENDING_LIMIT`（6,000）预算，并可能再次触发同一条规则的重复合并。
3. **`portrait.turns` 游标只增不减**：
   - `createTurnAccumulator`（`portrait.ts:1500`）每次拷贝全量历史 `seen` 字典并追加新 `sessionKey`。超过 `TWIN_CATCHUP_DAYS = 7` 的老会话永远不会再被 `readTwinSessions` 扫描，但其游标键值永久留在 SQLite 中。

### 3.6 【P2】数据源缺口、跨客户端注入断层与历史残留

1. **Notion 知识库尚未接入分身蒸馏**：`CONTEXT.md` 定义会话原文与知识库同为数字分身输入来源，目前管线仅消费会话与手工纠正，知识库中主动沉淀的长期思考尚未纳入。
2. **客户端注入覆盖不一致**：Claude Code、Codex、Grok、Gemini CLI 支持文件托管块自动更新，但 Cursor 在 `CLIENT_CATALOG`（`packages/core/src/clients/catalog.ts:71`）仍为 `{ kind: "copy" }`，分身升级后不会自动同步到 Cursor 全局或项目规则。
3. **已废弃 `brief` 变体的本地残留**：本地 `state.sqlite` 的 `portrait` 表及 `~/.you-brain/portrait/` 仍可能留有早期 `brief` 记录，卸载或拉取对账未做清理。

## 4. 分阶段收敛方案

### 阶段一：止血与管线边界修复（小改动、高确定性）

1. **补齐补跑上界与游标裁剪**（`portrait-drive.ts`、`portrait.ts`）：
   - `readTwinSessions` 增加上界 `sessionDay <= input.day`（仅当 `input.day` 早于今天时生效，当天正常运行保持不变），杜绝补跑时提前消费未来会话。
   - 保存 `portrait.turns` 前，对照 `sessions` 表的 `updatedAt`，裁掉最后更新早于 `shiftDateKey(ctx.day, -14)` 的 `sessionKey`。
2. **评测 `signal` 透传**（`portrait.ts`）：
   - `scoreProbes`、`scoreRound` 全链路接收并透传 `signal?: AbortSignal`。
   - `twinBefore` 的回退逻辑保持不变（见 3.4.3），留出隔离由第 1 条的补跑上界保证。
3. **修复 `buildTwinFixPrompt` 字节明细缺失**（`prompt.ts`）：
   - 只要 `problems` 涉及 `projects`（或 `input.docs.projects.trim() !== ""`），始终输出 `sectionSizes("projects", input.docs.projects)`，不受 `full` / `coding` 是否同时非空影响。
4. **低置信 `pending` 消费退役**（`portrait.ts`、`prompt.ts`、`schema.ts`）：
   - 合并与编码提案阶段由模型返回本次已采纳或明确丢弃的待定主张编号（或按高重合度匹配合并后正文），写入 `pending.jsonl` 前将其剔除。
5. **清理本地 `brief` 残留**（`portrait/service.ts`）：
   - `PortraitService.pull()` 对不在当前 `config.variants` 中的历史本地变体行与缓存文件做一次对账清理。

**验收**：单测覆盖「多日补跑不读未来会话」「评测中途 `abort()` 立即停止后续轮次」「混合变更修复 prompt 含 `projects` 字节数」「已升格 `pending` 主张不再写回」。

### 阶段二：重构 `projects` 实体对齐与准入门槛（核心治理）

1. **项目注册表与抽取上下文增强**（`twin.ts`、`portrait-drive.ts`、`prompt.ts`）：
   - 在 `projects.md` 每个项目组首节支持维护 `> aliases: 别名1, 别名2`（与现有 `> repos:` 同级解析与保留）。
