# 沉淀稳定性修复方案 Implementation Plan

**Goal:** 彻底解决每日沉淀（`consolidate`）长期超时失败、补跑卡死、话题文件同步 O(N) 放大、选话题 CPU 满载及阻塞 daemon 主循环的连锁问题，使沉淀能够在后台稳定、可续跑、低耗时地完成每日及 7 天补跑任务。

**Architecture:** 按“先低风险止血、再改调度与传输、最后做续跑与观测”的顺序分层治理：
1. **话题文件同步（`topic-files`）**：退场只按 `manifest` 精准删除；领养与残留清理改用单次 `drive.list` 建的目录索引，消除 1,180+ 次串行 `findByPath`。
2. **选话题与合并解析（`consolidate/select` + `topics/zones`）**：预建索引 + 日期 UTC 粗筛，把 `O(T × (S + E × T))` 降为单遍 `O(T + S + E)`。这是消除 CPU 阻塞的**唯一**手段（见 Task 5 说明）。
3. **补跑去重、话题文件解耦与退避重置（`consolidate/execute` + `run` + `daemon.ts`）**：多日补跑只在最后一天跑全量幂等步骤；`topic_files` 失败不再阻塞租约；改模型/Key 立即重置退避。
4. **LLM 流式与重试（`llm/http` + `llm/openai-compatible`）**：先实测网关是否真流式，再为沉淀显式开启 SSE 与三段超时；统一重试分类。
5. **daemon 调度隔离（`daemon.ts`）**：沉淀与话题文件写入迁出 `#run()` 锁，改为 detached job + 单飞 + 独立 `AbortController`，处理停机与换盘竞态。
6. **分身蒸馏减负与断点续跑（`consolidate/portrait*`）**：会话拉取按预算早停；按 prompt 哈希缓存各阶段模型结果，失败重试不重跑已完成阶段。
7. **状态观测（`daemon.ts`）**：`/api/status` 租约读取 stale-while-revalidate。

**Tech Stack:** TypeScript、Bun（`bun test`）、现有 `DrivePort` / `LlmBackend` / `SqliteStore` 游标与事件折叠，无新增第三方依赖。

## 背景与根因摘要（2026-11-19 实机排查）

- **时间线**：11-09～11-18 沉淀长期没写上租约，触发 `MAX_CATCH_UP_DAYS = 7`，从 `2026-11-13` 开始逐天补跑。09:14～16:20 因 `dzg/gpt-6.2-sol` 已下线，一直返回 404；16:30～21:10 切到 `grok/grok-4.7-build-fast` 后频繁撞上默认 60s 超时；21:11 把 `#createConsolidateLlm` 的超时提到 300s 后，`portrait` 仍然在 300s 整点超时失败。随后 `topic_files` 串行扫描 590 个已合并的历史话题，跑满 22 分钟，期间整个 daemon 主循环卡死。
- **五个叠加根因**：
  1. 非流式 HTTP + 代理长连接，导致 `portrait` 撞上 300s 兜底超时；失败后前面已完成的抽取/合并全部丢失；回退到默认 `#llm` 时还会退回 60s 超时。`completeJson` 遇到超时也会把报错塞进 prompt 当“纠偏”重试（`portrait.ts:1374-1377`）。
  2. `topic_files` 每次都把 590 个 `mergedInto !== null` 的历史话题无条件塞进 `retiredIds`（`sync.ts:108-110`），再逐个串行调 `findByPath`（`sync.ts:258-274`），共 1,180+ 次 Drive RPC，耗时 22 分钟。
  3. `selectTopicsChangedOnDay` / `selectChangedTopics` 嵌套扫描全量事件与会话（`select.ts:110-114`），`resolveMergedTopic` 每次调用都新建一个 985 项的 Map（`zones.ts:110`），单天同步 CPU 占满 50s 以上。
  4. 按日补跑时，`readTwinSessions` 先把 274 个会话文件全量拉下来，再按 `DAY_UNITS = 40_000` 截断；多日补跑重复执行幂等的全量步骤；`topic_files` 一失败当天就写不上租约（`execute.ts:164-171`）；改模型不会重置指数退避。
  5. `#consolidate` 与 `#writeTopicFiles` 直接在 `#tick()` / `#run()` 锁内 `await`（`daemon.ts:1612`、`1625`、`3881`），拖死全库同步与上传；`/api/status` 读租约的 `STATUS_DRIVE_WAIT_MS = 1_000` 过短，超时就直接返回 `lastFinishedAt: null`。

## Global Constraints

- **不改云端同步协议**：不修改 Drive 上的事件 schema、租约格式、分身文件格式和话题文件渲染内容；所有断点和状态缓存都存在本机 `SqliteStore` cursor 中（与现有 `portrait.turns`、`topicfiles.manifest` 同层）。
- **向后兼容现有调用与测试**：
  - `createOpenAiCompatibleBackend` 只在请求显式要求 `stream: true` 时才走 SSE；服务端返回 `application/json` 时自动回退普通解析。
  - `daemon.settled()` 必须等新的 detached job（`#consolidationJob`、`#topicFilesJob`）排空，保证现有集成测试语义不变。
  - `syncTopicFiles` 在 manifest 丢失/损坏时，仍能领养已有文件、清理已合并话题的残留文件，且不产生重复文件。
- **合入顺序约束**：Task 5 依赖 Task 2（否则同步 CPU 仍会卡住事件循环）；Task 6 的阶段缓存依赖 Task 4 的重试辅助函数；Task 5 的中止信号依赖 Task 4 在请求上加的 `signal`。
- **工具链约束**：一律使用 `bun`（`bun test`、`bun run typecheck`、`bun run build:daemon`）。
- **当前未提交改动**：`packages/core/src/daemon/daemon.ts` 里已有 `CONSOLIDATE_HTTP_TIMEOUT_MS = 300_000` 的未提交改动，本方案在其基础上继续演进，不回退已有意图。

## Review Focus

1. **话题文件增量零冗余请求**：590 个已合并、且不在 `manifest` 里的历史话题，日常同步时对它们的 `findByPath` 次数必须为 **0**；需要领养或清理残留时，整次同步只调用一次 `drive.list({ prefix: "topics" })`。（Task 1）
2. **选话题结果与原实现完全等价**：在包含多级合并链（`A → B → C`）、跨时区/DST 边界，以及 `session.refined` / `topic.assigned` / `conclusion.added` / `todo.added` / `topic.summary_rewritten` 的复杂事件流上，新实现输出的话题列表和排序必须与旧逻辑一致（对拍测试）；实库单天耗时 `< 50ms`（本机 benchmark）。（Task 2）
3. **主 tick 不被沉淀的 I/O 等待阻塞**：沉淀里的模型调用或 Drive 调用挂起时，采集扫描、上传、Drive pull/flush、`/api/status` 仍能正常推进。**注意**：detached job 和其他工作共用同一个 JS 线程，同步 CPU 计算照样会卡住事件循环，这部分由 Task 2 负责。`stop()` 要在 `BACKGROUND_STOP_MS` 内中止并退出，不触发已关闭 `SqliteStore` 的异常；换盘/登出时正在运行的沉淀会被中止，不会写到新盘。（Task 5）
4. **SSE 断流与残流不静默吞错**：服务端没返回 `[DONE]` / `finish_reason` 就断流，或超过空闲超时没有新字节，必须抛出可重试的 `LlmRequestError("network")`；流内的错误事件抛 `server`；收到 `: keep-alive` 或 `delta.reasoning_content` 时要刷新空闲计时器，但不拼进最终输出。（Task 4）
5. **分身断点续跑**：chunk 抽取失败后重试，不重跑已完成的 chunk；会话在重试间隙有新增内容时，未变化的 chunk 仍命中缓存；远端分身文件被别处修改后，合并阶段的 prompt 随之变化，自动重算，但已抽完的 claims 仍然复用。（Task 6）

### Task 1：修复 `topic-files` 串行扫描全部已合并历史话题

**Files:**
- Modify: `packages/core/src/topic-files/sync.ts`
- Test: `packages/core/test/topic-files/sync.test.ts`

**Design:**
- `readManifest` 返回 `{ manifest: Manifest; intact: boolean }`：`intact` 为 false 表示 raw 为 `null`、JSON 损坏或结构不合法；合法的空对象 `{}` 视为 intact。
- **目录索引（懒加载，整次 `syncTopicFiles` 最多一次）**：`loadTopicDirIndex(drive): Promise<Map<string, DriveEntry>>`，内部只调一次 `drive.list({ prefix: DRIVE_PATHS.topics })`，按 `entry.path` 建 Map。Google Drive 实现会遍历 `topics/` 和 `topics/history/` 两个目录并分页（`google-drive.ts:549-560`），请求数只和页数有关，与话题数无关。
- **退场（每次都执行，零额外查询）**：
  - `retiredIds` **只**收集 `Object.keys(manifest)` 中不在 `desiredIds` 里的 `topicId`，删掉 `sync.ts:108-110` 对 `book.topics` 的无条件遍历。
  - `retireTopic` 只按 `manifest[key].fileId` 调用 `trashFile`，删掉 `sync.ts:258-274` 的 `candidateTopicStems × zones` 循环（重名残留交给下面的残留清理）。
- **领养**：新话题不在 manifest 时，`findAdopt` 改查目录索引（按原有路径优先级 `expected` → 各候选 stem 的 active/history），不再逐个调 `findByPath`。
- **残留清理（低频执行）**：
  - 触发条件：`!intact`，**或**本机 cursor `topicfiles.swept_at` 缺失，**或**距上次清理超过 24 小时。后两个条件覆盖主设备 A→B→A 切换后 manifest 合法但已过期的情况：B 当主设备期间写入、后来又被合并的话题文件不在 A 的 manifest 里。
  - 逻辑：用目录索引筛出 `mergedInto !== null` 的话题在 `candidateTopicStems × ["active","history"]` 路径上的文件，`id` 不在 `protectedIds` 里的就 `trash`。
  - `drive.list` 失败时只记 warning，不计入 `failed`，也不写 `swept_at`，下次再试。全部成功后写 `swept_at = now`。
- **manifest 写入**：保持现在“每次实际写/删之后立即落盘”的崩溃安全语义。

### Task 2：将 `select.ts` 与 `zones.ts` 重构为单遍 `O(T + S + E)` 索引

**Files:**
- Modify: `packages/core/src/topics/zones.ts`
- Modify: `packages/core/src/consolidate/select.ts`
- Modify: `packages/core/src/consolidate/schedule.ts`（新增按日匹配辅助函数）

**Design:**
- **Step 0 先 profile**：在本机实库副本上对单天的 `topic_summaries` 做一次 CPU profile，确认 `selectChangedTopics`、`partitionTopics`、`#consolidationView()`（`listEvents` + `foldEventsCached`）、`recentTopicSessions` 各自的耗时占比，把结果记到本节。若 select 之外还有超过 1s 的热点，单独列项，不在本 Task 顺手改。
- `zones.ts`：
  - 导出 `createMergedTopicResolver(book: TopicBook): (topicId: string) => string`：用 `book.topics` 只建一次 `Map<topicId, mergedInto>`，逐步解析合并链并记忆化缓存；保留现有的环检测语义（遇到环返回当前节点）。
  - `resolveMergedTopic(book, topicId)` 保留签名，内部改为调用 resolver（单次调用的语义不变）。
  - 不切换到 `book.memory.parent`：两者是否在所有构造路径下都等价未经验证，以“与现状严格一致”为准。
- `schedule.ts`：导出 `createLocalDayMatcher(day: string, timeZone: string): (iso: string | null | undefined) => number | null`：
  - 预先算出 `day` 的 UTC 零点 `baseUtcMs`，粗筛窗口取 `[baseUtcMs - 14h, baseUtcMs + 38h]`（覆盖 UTC-12 到 UTC+14 以及 DST，留有余量）。
  - `Date.parse` 结果是 NaN 或落在窗口外，直接返回 `null`；窗口内再调 `localDayKey(new Date(ms), timeZone) === day`，命中则返回 `ms`。
  - `localDayKey` 抛错（时区非法）时返回 `null`，与 `instantOnLocalDay` 的 catch 语义一致。
- `select.ts`：
  - 内部函数 `indexDayActivity(book, input)` 一次构建：
    - `resolve = createMergedTopicResolver(book)`，`matchDay = createLocalDayMatcher(...)`
    - `sessionByKey = new Map(book.sessions.map(s => [s.sessionKey, s]))`（从 `book.sessions` 建，手工构造的 book 也等价）
    - 遍历 `book.sessions`：按 `session.topicId`（**不做**合并解析，与现状一致）汇总 `matchDay(sessionUpdatedAt[key])`。
    - 遍历 `book.memory.log`：
      - `topic.assigned` / `conclusion.added` / `todo.added`：`matchDay(event.ts)` 命中后，按 `resolve(event.data.topicId)` 更新 `lastChangeByTopic`。
      - `session.refined`：`matchDay(event.ts)` 命中后，取 `sessionByKey.get(event.data.sessionKey)?.topicId`（不做合并解析）。
      - `topic.summary_rewritten`：用 `Date.parse(event.ts)` 按 `resolve(event.data.topicId)` 记录全局最新的重写时间（不限当天）。
  - `selectTopicsChangedOnDay` 与 `selectChangedTopics` 共用 `indexDayActivity`；过滤、排序规则保持不变。
  - `recentTopicSessions`：先收集该话题的 `sessionKey` Set，再遍历一次 log，为相关会话汇总 `{ onDay, ms }`，复杂度从 `O(S_topic × E)` 降到 `O(E)`。

**Design:**
1. **多日补跑去重**：
   - `ConsolidationStep` 新增可选标记 `finalDayOnly?: boolean`。`mergeSuggestionsStep`、`topicFilesStep` 设为 `true`，它们都基于全量当前状态，与 `ctx.day` 无关。
   - `runConsolidation` 的输入新增 `isFinalDay: boolean`，由 `executeConsolidation` 按 `day === days[days.length - 1]` 传入；不是最后一天就跳过 `finalDayOnly` 步骤（不记入 `steps` 结果）。
   - 效果：7 天补跑时，前 6 天只跑按日推进的步骤（`todo_review`、`topic_summaries`、`portrait`、`portrait_eval`、`portrait_monthly`），最后一天再统一跑 `merge_suggestions` 和 `topic_files`。单天运行的行为完全不变。
2. **`topic_files` 不阻塞租约**：
   - `ConsolidationStep` 新增可选标记 `advisory?: boolean`，`topicFilesStep` 设为 `true`。
   - `runConsolidation` 中，`advisory` 步骤失败时仍记录 `{ id, ok: false, error }` 和 warning，但**不计入** `failed`，因此不影响 `result.ok` 和租约写入。
   - 理由：daemon 的 `#writeTopicFilesBody` 失败时本来就会把 `#topicFilesDirty` 设为 true 并设置防抖时间（`daemon.ts:2724-2728`），会自动重试；让它卡住整天的租约，正是补跑反复从头来的原因之一。
3. **配置/Key 变更立即重置退避**：
   - 新增 `#resetConsolidationBackoff()`：`backoffMs = 0`、`retryAtMs = null`，并把 `#lastConsolidation = null`，让下一个 tick 立即检查（否则还要再等 `INTERVALS.consolidationMs = 10 min`）。
   - 调用点：所有重建 `#llm` / `#consolidateLlm` 的位置（`daemon.ts:1147`、`2934`、`3219`、`4086` 附近，实现时用 grep 确认全部）、写入 LLM API Key 后、`roles.consolidation` 从关闭切到开启时。
