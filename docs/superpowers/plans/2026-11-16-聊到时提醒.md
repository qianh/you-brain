# 聊到时提醒 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 本人在任何入口聊到一个已有话题时，如果话题记忆里有一件会改变眼下做法的旧事，U-Brain 弹一句提醒；并先把超过 7 天的开放待办一次性关掉。

**Architecture:** 新模块 `packages/core/src/recall/` 只含纯逻辑和一个靠端口注入的 `RecallService`，不直接依赖 daemon。daemon 在采集扫描发现会话变化时把用户发言交给它，它匹配话题、调一次模型、按档位决定发 `recall`（弹通知）或 `recall_quiet`（只进列表）类型的 `reminder.issued`。桌面外壳只加一条规则：`recall_quiet` 不弹通知。

**Tech Stack:** TypeScript、Bun（`bun test`）、现有 `LlmBackend`、现有事件日志与提醒折叠；外壳是 Rust（Tauri）。

**Spec:** `docs/superpowers/specs/2026-11-16-聊到时提醒-design.md`

## Global Constraints

- 不改协议：`reminder.issued` 的 `kind` 是自由字符串，只新增两个取值 `recall`、`recall_quiet`。
- 不改会话提炼、不改每日沉淀、不改周回顾和早报。
- 任何失败都不得影响采集、上传、提炼：recall 的所有入口都在后台执行并吞掉异常。
- 模型调用走现有 `LlmBackend.complete`（受限补全加 JSON schema），不新增依赖。
- 数值照设计稿：用户发言上限 6,000 字；提醒正文不超过 60 字；同一话题 24 小时一条、全天 5 条（只约束「一般」档）；晚到的界线 5 分钟；重试间隔 1、5、30 分钟。
- 提示词全文在 Task 2，入库前已交本人过目；实现时原样使用，不改写。
- 提交说明用中文，默认 `feat:`，`git commit --no-verify`。每个 Task 结束提交一次。
- 每个 Task 结束跑项目全局用例：`bun test` 与 `bun run typecheck`。

## Review Focus

1. **daemon 重启或全量重扫**会把几千个旧文件重新过一遍：只有最近 10 分钟内更新的会话才考虑，旧会话一条模型调用都不能产生。（Task 4 测试）
2. **会话变了但没有新的用户发言**（助手还在输出、工具调用落盘）：不考虑，也不重复考虑。（Task 3 测试）
3. **话题已被合并**：匹配到的是被合并的话题时，按合并后的话题取记忆和记冷却。（Task 2 测试）
4. **同一条提醒被发两次**（重试成功后会话又变化、两台设备都看到同一个网页会话）：提醒 id 由会话和话题决定，已存在就不再发。（Task 3 测试）
5. **模型输出不合规**（空正文、带换行、超过 60 字、档位不在枚举里）：按校验失败走重试，不截断后硬发。（Task 2 测试）

```ts
export const RECALL_KIND = { notify: "recall", quiet: "recall_quiet" } as const;
export const RECALL_USER_CHARS = 6_000;
export const RECALL_TEXT_MAX = 60;
export const RECALL_MIN_SCORE = 0.25;
export const RECALL_CONCLUSIONS = 10;
export const RECALL_LATE_MS = 5 * 60_000;
export const RECALL_TOPIC_COOLDOWN_MS = 24 * 60 * 60_000;
export const RECALL_DAILY_LIMIT = 5;
export const RECALL_RETRY_DELAYS_MS = [60_000, 300_000, 1_800_000] as const;

export interface RecallMemoryItem { id: string; kind: "next_step" | "todo" | "conclusion"; text: string; day: string | null }
export interface RecallMemory { topicId: string; name: string; summary: string; lastActiveDay: string | null; items: RecallMemoryItem[] }
export type RecallDecision =
  | { say: false }
  | { say: true; grade: "important" | "normal"; text: string; basisId: string };

// match.ts：assignedTopicId 非空直接用（先解析合并），否则文本匹配，最高分低于 RECALL_MIN_SCORE 返回 null
export function matchRecallTopic(input: { assignedTopicId: string | null; userText: string; topics: readonly CandidateTopic[]; book: TopicBook }): string | null;

// memory.ts：items 为空时返回 null
export function buildRecallMemory(input: { book: TopicBook; topicId: string; sessionKey: string; sessionUpdatedAt: Readonly<Record<string, string>>; timeZone: string }): RecallMemory | null;

// prompt.ts
export const RECALL_SYSTEM_PROMPT: string;
export const RECALL_JSON_SCHEMA: object;
export function buildRecallPrompt(input: { memory: RecallMemory; userTurns: readonly string[]; today: string }): { system: string; user: string };
/** 输出不合规时抛错（调用方重试）；依据不在给出的记忆里时返回 { say: false }。 */
export function parseRecallDecision(raw: string, memory: RecallMemory): RecallDecision;

// delivery.ts
export function recallReminderId(sessionKey: string, topicId: string): string; // `recall:` + sha1(sessionKey + "\n" + topicId) 的前 16 位十六进制
export function decideRecallDelivery(input: {
  grade: "important" | "normal";
  elapsedMs: number;          // 从触发到出结果
  stillOnTopic: boolean;
  topicId: string;
  reminders: readonly ReminderRecord[];
  nowMs: number;
  timeZone: string;
}): { kind: "recall" | "recall_quiet" | null; reason: "ok" | "late" | "topic-cooldown" | "daily-limit" };
```

记忆条目的规则（`memory.ts`）：
- `next_step`：话题的 `nextStep` 非空时一条，id 为 `next`，无日期。
- `todo`：该话题下状态 `open` 的待办，id 为 `todo:<todoId>`，日期取创建日。
- `conclusion`：该话题最近 `RECALL_CONCLUSIONS` 条结论，id 为 `conclusion:<conclusionId>`。
- 来自当前 `sessionKey` 的待办和结论剔除。
- `lastActiveDay`：该话题下除当前会话外，最近一次会话更新的本地日期。
- 话题已合并时先 `resolveMergedTopic`，把并入的话题的条目一并算上。

冷却的规则（`delivery.ts`）：只数 `kind` 为 `recall` 或 `recall_quiet` 的记录，不看状态（点掉的也算提过）。「全天」按 `timeZone` 的本地日。

**提示词全文**（原样使用）：

```
你是 you-brain 的记忆提醒器。用户正在和某个 AI 助手对话，下面是他最近的发言，以及他以前在同一个话题里留下的记忆。判断这些记忆里有没有一条，现在提一句会改变他眼下要做的事。只输出一个 JSON 对象，不要 Markdown，不要解释。

规则：
1. 默认不说。大多数时候输出 {"say": false}。
2. 只有下面这类情况才说：有件没做完的事和他现在正在做的直接相关；他现在说的做法和以前定过的决定相反；他以前在同一个地方卡住过，记忆里有当时怎么过去的。
3. 他这次发言里已经提到的事不说。只是同属一个话题、和眼下的事没有直接关系的不说。
4. 要说时只挑一条，basisId 填那条记忆的 id，必须是输入里给出的 id。
5. grade 只有两个取值：important 表示不提会造成损失或返工，比如正要做的事和以前定过的决定相反，或者有个期限快到了；normal 表示提了有帮助，不提也没有损失。拿不准就填 normal。
6. text 是对他说的一句中文口语，不超过 60 字，不换行，写清是哪件事并带上那条记忆的日期（几月几日）。不写统计，不写「该话题还有 N 项待办」这类句子，不编造输入里没有的事实。
7. JSON 键名保持英文。
```

用户提示的结构（`buildRecallPrompt`）：`今天：<today>`、`话题：<name>`、`话题概要：<summary>`、`上次聊这个话题：<lastActiveDay 或「未知」>`、`## 记忆`（每行 `[<id>] <日期或「-」> <text>`，单条截到 300 字）、`## 他最近的发言`（从最新往回取，合计不超过 `RECALL_USER_CHARS`，按时间正序输出）、`## 输出 JSON schema`。

```ts
// log.ts：追加一行 JSON 到 <dataDir>/recall-log.jsonl（0600）；超过 2,000 行时只留最新 2,000 行
export interface RecallLogEntry {
  ts: string; sessionKey: string; topicId: string | null;
  outcome: "no-topic" | "no-memory" | "muted" | "silent" | "issued" | "suppressed" | "duplicate" | "failed" | "gave-up";
  grade?: "important" | "normal"; kind?: "recall" | "recall_quiet"; reason?: string; text?: string;
}
export function createRecallLog(path: string): (entry: RecallLogEntry) => void;

// service.ts
export interface RecallPorts {
  llm(): LlmBackend | null;
  book(): TopicBook;
  candidateTopics(): CandidateTopic[];
  sessionUpdatedAt(): Readonly<Record<string, string>>;
  reminders(): readonly ReminderRecord[];
  topicMuted(topicId: string): boolean;
  emit(data: { reminderId: string; kind: string; topicId: string; text: string }): Promise<void>;
  cursors: { get(key: string): string | null; set(key: string, value: string): void };
  log(entry: RecallLogEntry): void;
  nowMs(): number;
  timeZone(): string;
}
export const RECALL_CONSIDERED_CURSOR = "recall.considered";
export const RECALL_STILL_ON_TOPIC_MS = 10 * 60_000;
export class RecallService {
  constructor(ports: RecallPorts);
  /** 不阻塞、不抛错。userTurns 是这个会话里用户发言的全量，按时间正序。 */
  consider(input: { sessionKey: string; userTurns: readonly string[] }): void;
  /** 跑到期的任务（首次和重试），一次一个。daemon 每个 tick 调一次。 */
  tick(): Promise<void>;
  pending(): number;
}
```

行为：
- `consider` 记下这个会话的用户发言条数和时刻。条数没有比上次多，直接返回（会话变了但没有新的用户发言）。
- 话题匹配不上记 `no-topic`；话题被静音记 `muted`；`buildRecallMemory` 返回 null 记 `no-memory`。这三种都不调模型，也不记为已考虑。
- 「已考虑」集合存在游标 `RECALL_CONSIDERED_CURSOR`，元素是 `{ sessionKey, topicId, ts }`，只在模型明确返回不说、或提醒已发出、或被冷却压下之后写入；超过 7 天的条目在写入时清掉。
- 同一 `(sessionKey, topicId)` 已在集合里、或已有任务在排队，不再入队。
- `tick` 取一个到期任务：`llm()` 为 null 或调用抛错、或 `parseRecallDecision` 抛错，按 `RECALL_RETRY_DELAYS_MS` 安排下一次，记 `failed`；三次重试都失败记 `gave-up` 并丢弃任务，不写入已考虑。
- 决定要说时：`recallReminderId` 已存在于 `reminders()` 记 `duplicate`；否则用 `decideRecallDelivery`，`elapsedMs` 从该任务第一次入队算起，`stillOnTopic` 为「这个会话最近一次带来新用户发言的 `consider` 距今不超过 `RECALL_STILL_ON_TOPIC_MS`」。`kind` 为 null 记 `suppressed`，否则 `emit` 并记 `issued`。
- 重试任务只在内存里，daemon 重启后不恢复；因为没写入已考虑，本人在该会话再发消息时会重新入队。

### Task 4: 接进 daemon

**Files:**
- Modify: `packages/core/src/daemon/daemon.ts`（`#scanBody` 约 1941–1960 行的循环、`#runDue` 约 1380–1395 行、`#indexInboxFile` 约 2228–2270 行、构造与 `#openServices`）
- Modify: `packages/core/src/reminders/due.ts`（导出 `topicControl`，它返回 `{ muted, ignored }`；`topicMuted` 端口取其中的 `muted`，入参里的 `actions` 用现有 `#issueReminders` 同样的来源）
- Test: `packages/core/test/daemon/recall.test.ts`

**Interfaces:**
- Consumes: `RecallService`、`createRecallLog`
- Produces: 无新的对外接口。

接法：
- **开关**：`shared.reminders.notifications` 为 false 时整个功能不运行，不调模型。
- **本机会话**：`#scanBody` 的循环里，哈希变了且 `meta.updatedAt` 距今不超过 10 分钟的会话，收集它的 key。循环结束后对每个 key 在后台执行（不 `await`，吞异常）：`#materialize(live)` → 取 `role === "user"` 的 `turn.text` → `recall.consider`。
- **网页会话**：`#indexInboxFile` 里 `web` 为真、内容有变化、`updatedAt` 距今不超过 10 分钟，且 `#canProcessWebSessions()` 为真时，`parseWebSession(text)` 取用户发言 → `recall.consider`。只在网页会话处理设备上做（`resolveWebProcessor`，未指定时就是主设备），避免两台设备各考虑一遍。
- **执行**：`#runDue` 里在网页会话提炼和历史回灌之间加一段，写法与它们相同：`this.#recallJob ??= this.#recall.tick().catch(() => {}).finally(() => { this.#recallJob = null; })`，每个 tick 都检查，不设间隔。
- **排队**：不另做优先级。CLI 后端的槽位先到先得，回灌是一条一条请求的，所以 recall 最多等一个正在跑的调用。
