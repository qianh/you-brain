# 待办核对与跟进推送 · 设计

> 2026-11-16 ｜ 状态：暂缓。本人看过后认为每日定时提醒不如「聊到时提醒」「到点提醒」重要，排在第三做；先做 `2026-11-16-聊到时提醒-design.md`。轮到它时再审阅。

> 参照：Anthropic《Components of agent memory》（2026-11-06）里的「做梦」：离线时回看原文，核对和整理已有记忆。

## 为什么做

本人要的是像 Muse 那样：基于聊过的内容主动推「这件事该做了」「这个值得关注」，其中一部分由系统先查好资料，把结论交给本人核对。现在做不到，原因有三个（2026-11-16 本机数据）：

1. **提醒是统计数字。** 早报原文是「昨日结论 205 条…未完成待办 653 件。建议跟进：海运运价预测、Codex CLI用法、Agent Reach」。早报 23 条、周回顾 5 条，全部被点掉。
2. **待办只增不减。** 909 条里 661 条还开着，单个话题最多 114 条。会话提炼只会加待办，没有机制在事情做完或作废后关掉它，所以挑不出真正该推的那几件。
3. **每日沉淀是关的。** `roles.json` 里 `consolidation.enabled` 为 `false`，最近一次话题概要重写是 2026-11-10。

## 目标

- 开着的待办是真的还没做的事。
- 每天早上收到最多 3 条具体的跟进事项，每条说清是什么事、停在哪。
- 第二期：需要查资料的事项，系统先查，把结论和出处交给本人核对。

## 不做

- 不做「对照原文纠正话题概要和结论」。没有实际发生过的错误支撑；纠正结论还要加协议事件。
- 不建 wiki，不给话题之间加链接。
- 不做月度回顾、时间节点提醒、跨项目建议（TODO I4～I6）。
- 不监控外部新信息。推送只来自聊过的内容。
- 不改周回顾。
- 不新增提醒的操作按钮，沿用现有的。

## 反目标

- 推送又变回统计数字或话题名罗列。
- 没有原文依据就自动关掉待办。
- 没经本人核对的查证结论被写成话题结论，变成记忆。
- 一天推送超过 3 条。

## 方案取舍

| 方案 | 内容 | 结论 |
|---|---|---|
| 一 | 只核对待办、挑选跟进事项，不查证 | 不满足「查完给结论」 |
| 二 | 方案一加查证，分两期 | **本人选定（2026-11-16）** |
| 三 | 整件事交给指挥台的夜间任务，由模型自己决定 | 产出不稳定、难测，出错分不清是哪一步 |

选方案二的理由：推送准不准取决于待办干不干净，查证值不值取决于挑得准不准，顺序只能是先核对、再挑选、再查证。

## 一、待办核对（每晚）

每日沉淀新增步骤 `todo_review`，排在 `topic_summaries` 之前。

**核对范围**：当天有变化的话题（沿用 `selectTopicsChangedOnDay`）里状态为 `open` 的待办。当天没动过的话题不看，因为没有新原文可以对照。

**输入**：每个话题一次模型调用，给它这个话题的开放待办，加上当天该话题下各会话的完整原文（用户和助手的发言都要）。

- 沉淀现在只能拿到用户本人的发言（`ConsolidationPortrait.sessions`）。需要给 `ConsolidationContext` 加一个读完整原文的入口，数据来源与它相同。
- 原文超出预算时保留最后的部分，上限 24,000 字，与会话提炼一致。事情做没做完看的是结尾。（我定的）

**输出**：每条待办一个判断，`keep`、`done` 或 `dropped`。判 `done` 或 `dropped` 必须附一句原文引用作依据。

**失败关闭**：

- 程序检查引用是否原样出现在给模型的原文里。不出现就按 `keep` 处理。
- 模型输出校验不过重试一次，仍不过则这个话题当晚不动。
- 单个话题失败不影响其他话题；全部失败则步骤失败。

**写入**：对判 `done` 或 `dropped` 的待办发 `todo.status_changed`，`by: "auto"`。当晚关了哪些、依据是哪句，写进游标 `consolidate.todo_review`，供状态页查看和事后追查。

**不按时间自动作废**：7 天清理只做一次。隔几周回到一个话题时，没做完的事正是「聊到时提醒」最该提的，所以待办只在原文显示已完成或作废时才关。每日推送的候选仍只看 7 天内的。

## 二、跟进事项（每晚挑，早上推）

每日沉淀新增步骤 `follow_ups`，依赖 `todo_review` 成功。

**候选**：7 天内活跃的话题的概要和下一步，加上它们的开放待办。

**一次模型调用**，挑出最多 3 件，每件包含：

- `topicId`，以及对应的 `todoId`（没有对应待办时为空）
- `text`：一句话，不超过 80 字，写清是什么事、停在哪。不写统计，不只写话题名
- `needsResearch` 和 `question`：这件事是否要先查资料才能推进、要查什么。第一期只记录，不执行

**不重复**：近 3 天推过的同一条待办不再推；没有对应待办的事项，同一话题 3 天内只推一次。（我定的）

**没有值得推的就输出空**，程序不凑数。

**存放**：结果写进游标 `consolidate.follow_ups`，带日期。

**推送**：早报时间到了，主设备读这个游标，每件事发一条提醒，类型 `follow_up`，带 `topicId`，点开跳到话题。提醒类型在协议里是自由字符串，不用改协议。

- 现有的统计式早报（`morning_digest`）不再生成。（我定的）
- 游标不是昨晚的（沉淀没跑或失败）或结果为空时，当天不推。沉淀没跑的告警状态页已有。
- 系统通知沿用现有投递判定，一件一条，一天最多 3 条。

推送的样子：

```
海运运价预测：11-13 说等拿到 10 月运价数据再重训，数据还没接。
Agent Reach：上次停在 Exa MCP 接入核对，核对清单还剩 2 项。
```

## 三、第二期：查证（只定方向）

对 `needsResearch` 为真的事项，夜里先查资料，把结论和出处附在推送里，标明「待你核对」。每晚最多查 3 件。

已定：

- 查到的结论在本人确认前不写成话题结论。
- 查证失败或超时，这件事照常推送，只是不带结论。

未定，第二期开工前单独定：

- **谁来查。** daemon 调本机 CLI 时明确禁用了工具和联网搜索（`packages/core/src/llm/cli/drivers.ts`）。指挥台 v1 的 CLI agent 执行者在 2026-11-03 改用 dsh 运行时（`eb84b76`）时已经移除。两条路：给 CLI 后端加一个只开联网搜索的查证模式，或者经 dsh 执行。
- **值不值得做。** 第一期跑一到两周后看两个数：被标成需要查证的事项占多少，跟进提醒被点掉的比例有没有从现在的 100% 降下来。

## 前置条件

- 本人打开每日沉淀（`consolidation.enabled`）。两步都跑在沉淀里。
- 一次性清理已在「聊到时提醒」那一件里做完。

## 留给实现者

- `ConsolidationContext` 读完整原文的入口怎么接到 daemon。
- 两个步骤的提示词和 JSON schema。提示词入库前交本人过目。
- 状态页怎么展示当晚关掉的待办。

## 验收

1. 当天会话里明确做完的待办，第二天早上已是完成状态，游标里能看到依据的原文。
2. 模型给不出原文引用，或引用在原文里找不到，待办保持开放。
3. 本人手动改过状态的待办，自动核对不动它。
4. 早上的提醒最多 3 条，每条是一句具体的事，点开跳到对应话题。
5. 沉淀没跑的那天早上不推送。
6. 连续三天不出现同一条待办的推送。
7. 不再出现统计式早报。
8. 项目全局测试、类型检查通过。
