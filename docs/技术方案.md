## 1. 总体架构

```
   设备 A（Mac 桌面）              设备 B（工作电脑）             设备 S（服务器，主设备）
 ┌──────────────────────┐    ┌──────────────────────┐    ┌──────────────────────┐
 │ Tauri 菜单栏外壳       │    │ Tauri 菜单栏外壳       │    │ （无界面）              │
 │   └ WebView：Web UI   │    │   └ WebView：Web UI   │    │                      │
 │ you-brain 核心服务     │    │ you-brain 核心服务     │    │ you-brain 核心服务      │
 │  采集 · 上传 · 提炼     │    │  采集 · 上传 · 提炼     │    │  网页会话提炼 · 全局沉淀 │
 │  同步 · 本地 SQLite    │    │  同步 · 本地 SQLite    │    │  同步 · 本地 SQLite     │
 │  MCP · markdown 输出   │    │  MCP · markdown 输出   │    │  CLI · MCP            │
 └──────────┬───────────┘    └──────────┬───────────┘    └──────────┬───────────┘
            │       各自只写自己的事件文件 / 会话文件，读取所有人的        │
            └─────────────────────────────┼─────────────────────────────┘
                                          ▼
                     Google Drive：brain-hub/（原文 + 协议数据，唯一的共享存储）
                                          ▲
              浏览器插件（独立项目，只上报网页会话原文）、外部 bot（虚拟设备）
```

要点：

- **没有中心服务器**。Drive 是唯一的共享存储和同步通道。
- **每台设备运行同一个核心程序**，只是角色不同：普通设备、主设备、网页会话处理设备。
- **单一写入方规则**：每个文件只有一个写入方，避免并发冲突（见第 4 节）。
- 本地 SQLite 是 Drive 数据的**派生副本**，丢了可以从 Drive 完整重建。

## 2. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 核心服务 | TypeScript + Bun | 用 `bun build --compile` 编译成单个可执行文件，桌面和服务器共用 |
| 本地存储 | `bun:sqlite` + FTS5 | 替代 BrainHub 的 better-sqlite3 |
| 语义搜索 | `@huggingface/transformers` + `multilingual-e5-small` | 沿用 BrainHub；在 Bun 编译产物中的可用性需在 M0 验证 |
| Drive | `googleapis` | 沿用 BrainHub 的 drive 模块并做改造 |
| MCP | `@modelcontextprotocol/sdk` | stdio 模式，由 `you-brain mcp` 启动 |
| 模型调用 | OpenAI 兼容协议客户端 | 覆盖 DeepSeek / GLM / Qwen / Kimi / OpenAI / Ollama；Claude 使用原生协议适配 |
| 校验 | `zod` | 协议、配置、模型输出的校验 |
| 桌面外壳 | Tauri v2 | 托盘、全局快捷键、开机自启、通知插件；WebView 加载 Web UI |
| Web UI | 前端框架待定（建议 React + Vite，用 bun 构建） | 由核心服务在 `127.0.0.1` 提供 |
| 密钥 | macOS Keychain / Linux Secret Service | 沿用 BrainHub 的 secret-store |
| 包管理 | bun | 统一使用 bun |

## 5. 会话采集与上传

### 5.1 采集

- **触发**：文件监听（fs watch）各来源目录 + 低频全量扫描兜底（默认 10 分钟）。
- **会话身份**：`conversationKey = sha256(source + "\0" + conversationId)`，沿用 BrainHub。
- **空闲判断**：会话文件 5 分钟无新写入时，视为空闲（可配置）。
- **适配器接口**：

```ts
interface SourceAdapter {
  id: string;                          // 如 "claude-code"
  defaultRoots(): string[];            // 默认扫描路径
  discover(roots: string[]): AsyncIterable<SourceFile>;
  parse(file: SourceFile, opts: CaptureOptions): Promise<NormalizedSession[]>;
  // 识别"恢复会话"时复制历史到新 ID 的情况，返回被延续的原会话 ID
  continuationOf?(session: NormalizedSession): string | null;
}
```

- **各适配器需要验证的事项**：恢复会话（`--resume` / `--continue` 等）时是沿用原会话 ID，还是生成新 ID 并复制历史。如果是后者，要通过 `continuationOf` 关联，并且在提炼时只处理新增部分，避免同一段历史被重复计算。
- **会话判定**（`adapters/conversation.ts`）：一条会话必须包含至少一条用户自己输入的消息，才值得上传和提炼。CLI 启动时注入的 `AGENTS.md` 指令、`<environment_context>` 等不算。实测 Codex 的 6735 个文件里只有 189 个是真实对话，不过滤会拖垮后续所有环节。不要求有助手回复——会话是在进行中被采集的，等待回复会漏掉正在写的对话。
- **行式数据源**：T3 Code 把全部会话存在一个 SQLite 库里，不是一文件一会话。它的 `SourceFile.path` 形如 `<state.sqlite>#<threadId>`，文件指纹用整个库文件的 mtime 加行 id。T3 从其他工具导入的会话以 `import:` 开头，跳过。

### 5.2 上传：原地更新（相对 BrainHub 的关键改动）

BrainHub 现状（`upload-service.ts:318-355`）：每次上传都新建候选文件，读回校验后，选出 `updatedAt` 最新的作为正式文件，把其他文件移入回收站，**因此每次更新 fileId 都会变**。

这是 BrainHub 的实现选择，不是 Drive 的限制：Drive 的 `files.update` 支持替换内容并保持 fileId 不变，BrainHub 自己也实现了带 etag 的 `upsert`（`google-drive.ts:524`），只是上传流程没有使用。BrainHub 选择候选文件方案，是为了在无协调的情况下让多设备并发上传收敛，并且做到先校验再生效；而当时没有"链接固定"的需求（会话引用不是 fileId）。you-brain 用 etag 乐观锁处理并发，用 `md5Checksum` 比对完成校验，同样能达到这两个目标。

you-brain 改为：

```
upload(session):
  key = conversationKey(session)
  existing = localIndex.fileIdOf(key) ?? drive.findByAppProperty("brainhubKey", key)
  if existing.length == 0:
      create 文件（appProperties 含 brainhubKey 等）→ 记录 fileId
  else:
      canonical = existing 中 createdTime 最早的一个
      if 远端内容不比本地新（比较 updatedAt 与消息数）:
          files.update(canonical.id, 新内容, If-Match: etag)   # fileId 不变
          412 冲突 → 重新读取、比较后重试
          校验：Drive 返回的 md5Checksum 与本地内容的 md5 一致才算成功
      if existing.length > 1:                                  # 并发创建产生的重复
          把较新的内容合并进 canonical，再把其他文件移入回收站
  文件名随会话标题变化时只改名，不影响 fileId
```

- `appProperties` 沿用 BrainHub 的 `brainhubKey / source / conversationId / deviceId / updatedAt / contentSha256`，新增 `ybSchema`（原文格式版本）。
- **节流**：会话空闲后上传；会话持续活跃时最多每 5 分钟上传一次。
- 原文格式沿用 BrainHub 的 markdown 渲染（`capture/normalize.ts`），保证历史数据兼容。

### 5.4 调度：慢操作不占串行 tick

daemon 的 tick 是一条串行链（`daemon.ts` 的 `#run`），一次只做一件事。把"要等模型"或"要等网络"的工作放进去，后面的拉取、刷新状态、收件箱索引都会被饿死——实测中出现过 `lastSyncAt` 停更十几分钟。

所以按耗时把工作分成三类：

| 类别 | 做法 | 位置 |
|---|---|---|
| 快操作（毫秒级） | 留在 tick 里串行执行 | 扫描、状态判断、事件派发 |
| 网络 IO（秒级） | 独立的连续循环，不占用 tick | 会话上传 `#uploadLoop` |
| 模型调用（几十秒） | 独立循环 + 互斥，一轮一个 | 网页会话 `#processWebSessions`、历史回填 `#refineBackfill` |

三条附加规则：

- **上传与同步分时**：tick 的 flush / pull / 收件箱索引期间置 `#syncBusy`，上传循环让路。否则上传占满 Drive 连接，变更流拿不到窗口。
- **上传只同步，不提炼**：写 Drive 和调模型是两件事，绑在一起会让一次上传从 6 秒变成 64 秒，几千个会话的历史欠账要按天算。提炼统一由 `#refineBackfill` 负责，它只处理本机、近 30 天、已上传的会话，按 `updated_at` 从新到旧。
- **遍历轮转**：批处理的起点每轮后移，单个慢会话或持续失败的会话不会占满预算、让其他会话永远轮不到。

### 5.5 采集指纹：重启不全量重扫

`capture.files` 游标保存每个源文件的 `stamp`（mtime + size）、所属会话 key、以及该会话的元数据（`CaptureMeta`）。

- 重启后按指纹跳过未变化的文件，只解析变化的。实测 9,596 个文件的重扫从 7 分钟降到 665 毫秒。
- 元数据必须一起保存：`skipFile` 要求 `cursor.sourcePath === path`，而 `sourcePath` 来自内存里的会话表；不恢复元数据，命中的指纹会因为"没有主人"被丢弃，于是又退回全量解析。
- 恢复时按库里有没有 `file_id` 决定排队状态：没有的说明从未上传过，重新入队；有的标记为已上传，避免重启后把全部会话重推一遍。
- 未变化的扫描结果不带元数据，写回游标时要保留旧值，否则下次重启就恢复不出来了。

### 6.3 事件日志

每台设备只往自己的 `events/<deviceId>/<YYYY-MM-DD>.jsonl` 写入，每行一个事件。Drive 不支持追加写，所以按天分片：设备每次 flush 时原地更新当天的文件（同样使用 fileId 原地更新）。

**事件通用字段**：

```json
{
  "v": 1,
  "id": "全局唯一 ID（ULID）",
  "ts": "ISO8601",
  "device": "deviceId",
  "seq": 128,
  "type": "事件类型",
  "data": { }
}
```

**事件类型**：

| 类型 | data | 产生方 |
|---|---|---|
| `session.refined` | `sessionKey, fileId, source, title, summary, refinedUpTo（已提炼到第几条消息）` | 会话所在设备 / 网页会话处理设备 |
| `topic.created` | `topicId, name, aliases` | 提炼或用户操作 |
| `topic.assigned` | `topicId, sessionKey` | 提炼或用户操作 |
| `topic.unassigned` | `topicId, sessionKey` | 用户操作（拆分） |
| `topic.renamed` | `topicId, name, aliases` | 用户操作 |
| `topic.status_changed` | `topicId, status, by: auto/user` | 提炼 / 用户 / 沉淀 |
| `topic.merged` | `fromTopicId, intoTopicId` | 用户确认合并 / 沉淀 |
| `topic.summary_rewritten` | `topicId, summary, nextStep` | 主设备沉淀（P1） |
| `conclusion.added` | `conclusionId, topicId, text, sessionKey` | 提炼 |
| `todo.added` | `todoId, topicId, text, sessionKey, confidence` | 提炼 |
| `todo.status_changed` | `todoId, status: open/done/dropped, by` | 提炼 / 用户 |
| `portrait.correction` | `correctionId, variant, section, text` | 用户（P1） |
| `portrait.correction_applied` | `correctionId, snapshot` | 沉淀方（P1） |
| `reminder.issued` | `reminderId, kind, topicId, text` | 主设备（P1） |
| `reminder.action` | `reminderId, topicId, action: reactivate/done/snooze/mute/ignore, until` | 用户（P1） |

### 6.4 事件合并规则（每台设备在本地执行）

1. 拉取所有设备的事件，按 `(ts, device, seq)` 全局排序后依次应用，结果确定、可重放。
2. **字段级后写入者胜出**：名称、状态、概要等字段取最后一次事件的值。
3. **用户优先**：`by: user` 的状态变更，不会被之后 `by: auto` 的事件覆盖，除非用户再次修改。
4. **合并**：`topic.merged` 建立 `from → into` 的映射，之后所有指向 `from` 的事件自动重定向到 `into`。
5. **并发新建同名话题**：两台设备几乎同时新建了规范化名称相同的话题时，合并时自动按 `(ts, topicId)` 最小者为准，等同于一次自动合并。
6. **幂等**：事件按 `id` 去重，重复拉取不会重复应用。
7. **会话提炼取最新**：同一会话的多次 `session.refined` 中，`refinedUpTo` 最大的那次生效。

### 6.5 活跃区与历史区（派生计算，不写事件）

```
lastActive(topic) = max(相关会话的 updatedAt, 话题最后一次用户操作时间)
候选 = 状态不是"已完结"，且 now - lastActive < 历史天数（默认 30）
活跃区 = 候选按 lastActive 降序排列后的前 N 个（N 默认 10）
历史区 = 其他所有话题
```

- 历史话题有新会话归入时，`lastActive` 更新，自然回到活跃区。
- 规则是纯函数，各设备算出的结果一致。

## 7. 会话提炼

### 7.1 触发与归属

| 会话类型 | 负责提炼的设备 |
|---|---|
| 本地 CLI 会话 | 会话所在设备 |
| 网页会话（`inbox/web-*/`） | `roles.webProcessor`（默认是主设备） |

- 本地会话：空闲 5 分钟后，先上传再提炼。
- 网页会话：处理设备通过 Drive 变更游标发现新增或更新的网页会话文件，空闲 5 分钟（以文件的 `updatedAt` 判断）后提炼。

网页会话处理已实现（`packages/core/src/web-sessions/`）：所有设备索引 `inbox/web-*`，待提炼由本地库的 `refinedUpTo < msgCount` 推导；只有 `resolveWebProcessor(roles)` 指向的设备在空闲后提炼，每 60 秒最多 3 个。浏览器插件的真实文件格式尚无样本；文件缺 `turn_count` 时按正文数轮次。角色字段可以在协议、`you-brain devices --set-web-processor` 和设备页里读写。

### 7.2 增量提炼

本地存储每个会话的 `refinedUpTo`（已提炼到的消息序号）和上次的提炼结果。

**模型输入**：

```
- 上次提炼结果（标题、概要、已有结论、已有待办），首次提炼时为空
- 新增消息：第 refinedUpTo+1 条到最新一条（过长时截断最早的部分）
- 候选话题：活跃区全部话题 + 历史区最近 20 个话题（名称、别名、一句话概要）
- 当前开放的待办（属于候选话题的）
```

**模型输出**（JSON，用 zod 校验，失败时重试一次）：

```json
{
  "title": "…",
  "summary": "…",
  "topic": { "action": "assign | create", "topicId": "…", "name": "…", "aliases": [] },
  "conclusions_added": ["…"],
  "todos_added": [{ "text": "…", "confidence": 0.9 }],
  "todos_completed": ["todoId"]
}
```

- 提示词要求：**优先归入已有话题**，只有明显是新事情时才新建；只输出置信度不低于 0.8 的待办。
- 输出转换成第 6.3 节的事件写入本机事件日志，然后推送。
- 第一版一个会话只归入一个主话题。

### 7.3 模型后端

```ts
interface LlmBackend {
  id: string;
  complete(req: { system: string; user: string; jsonSchema?: object }): Promise<string>;
  test(): Promise<void>;
}
```

- P0：`openai-compatible`（DeepSeek / GLM / Qwen / Kimi / OpenAI / Ollama / 自定义地址）、`anthropic`。

## 8. 同步

### 8.1 推送

- 事件：每产生一批就写入本地 outbox，合并后每 30 秒 flush 一次，原地更新当天的事件文件。
- 设备心跳：每 5 分钟一次。
- 会话原文：见 5.2。

### 8.2 拉取

- 使用 Drive `changes.list` + 页游标（startPageToken），游标保存在本地，沿用 BrainHub 搜索索引的做法。
- 默认每 60 秒轮询一次（可配置）；设备唤醒、网络恢复、GUI 打开时立即触发一次。
- 拉到的变化分三类处理：
  - 事件文件变化 → 读取新增行 → 合并（6.4）→ 刷新本地话题册
  - inbox 文件变化 → 只下载本机范围内的（`inbox/<本机>/`，本机是网页会话处理设备时加 `inbox/web-*`），更新会话索引和搜索索引；范围外的记一笔路径就不管了，它们由各自的设备提炼
  - 数字分身 / 配置变化 → 拉取到本地，刷新输出和 CLI 注入
- **新设备首次同步**：全量读取 `you-brain/` 下的协议数据和 `digital-twin/`，重放事件生成话题册；会话原文不下载，只建立索引（标题、概要来自事件），搜索索引按需后台构建。
- **搜索范围**：本地索引只覆盖本机会话。要搜别的设备上的内容时，走 Drive 全文搜索拿候选，再按需下载单篇原文截取片段——这样既不用在每台设备上建全量索引，也不会把别人的会话原文长期留在本机。
- **`WEB_PROCESSOR_MISSING` 提示**：不依赖本机索引判断（非处理设备不下载 web 文件），改为 pull 时观察到 `inbox/web-*` 存在就记一个 `webinbox.seen` 游标。

### 8.3 离线

所有写操作先进入本地 outbox，联网后按顺序推送；读操作完全基于本地 SQLite。

## 11. 全局沉淀（P1，已实现）

`packages/core/src/consolidate/` 实现了租约、按日补跑（最多 7 天）和步骤框架；步骤为 `topic_summaries`、`merge_suggestions`、`portrait`（仅全量版；备份到 `consolidate-backup/`、`ifMatch` 更新 latest、再写版本快照，冲突 / 变短 / 无变化则跳过）、`topic_files`（`topic-files/`）。任一步失败则当天租约不写，退避 30 分钟到 6 小时重试。设置页可改开关和时间，显示上次沉淀并可手动触发（`POST /api/actions/consolidate`）。提醒由独立的定时流程生成（第 12 节），不是沉淀步骤。

- **执行者**：`roles.mainDevice`，并且 `consolidation.enabled = true`。
- **防重复**：执行前读取 `leases/consolidate.json`。如果当天已有其他设备完成（切换主设备时可能出现），就跳过；完成后写入 `{ date, deviceId, finishedAt }`。
- **补跑**：主设备离线错过的日期，上线后按日期顺序补跑。
- **步骤**：
  1. 为当天有变化的话题重写概要和下一步 → `topic.summary_rewritten`
  2. 生成相似话题的合并建议（写入每周回顾，不自动合并）
  3. 更新数字分身：以"现有版本 + 当天会话提炼 + 未应用的纠正"为输入，生成新版本；先按现有规则保存快照，再原地更新 latest 文件
  4. 原地更新 `topics/TOPICS-latest.md` 和各话题详情文件；话题进入历史区时，把详情文件移到 `topics/history/`（移动不改变 fileId）
  5. 生成提醒 → `reminder.issued`（实现上由主设备的独立定时流程完成，不挂在沉淀步骤里）
- **白天的话题文件**：话题册变化后，主设备防抖 5 分钟，批量更新 Drive 上受影响的话题文件。
- **状态告警**：任何设备发现 `leases/consolidate.json` 中的最后完成时间超过 1 天，就在状态页标红。

## 12. 提醒（P1，已实现）

`packages/core/src/reminders/`：主设备按本地时区生成，事件折叠后落库，`GET /api/reminders`、MCP `get_reminders` 与 `~/.you-brain/REMINDERS.md` 返回真实数据；设备活跃判定见 `delivery.ts`，桌面外壳按键鼠空闲上报活动并弹系统通知。系统通知在真机上未验证。

| 类型 | 生成规则 |
|---|---|
| 停滞 | 活跃话题有开放待办，且 `now - lastActive ≥ 7 天` |
| 历史话题 | 历史区中有开放待办的话题，每周回顾时提醒，**每周最多 5 条**：按开放待办数降序、最后活跃时间降序取前 5，其余由每周回顾那一条承载 |
| 每日早报 | 昨日新增的结论和待办 + 建议跟进的 1–3 个话题 |
| 每周回顾 | 本周活跃话题、新增结论、停滞话题、历史话题、合并建议 |

- 用户操作产生 `reminder.action` 事件；`ignore` 累计 3 次后，该话题不再提醒，直到它重新活跃。
- **通知投递**：每台设备都能看到提醒，但只有 `lastActiveAt` 在 10 分钟内且时间最新的那台设备弹出系统通知。其他设备只显示角标。

## 14. 进程与界面

### 14.1 进程模型

```
you-brain daemon      常驻核心服务：采集、上传、提炼、同步、调度、本地 HTTP API
you-brain mcp         MCP stdio 服务（由 AI 客户端拉起，只读本地库，写操作转发给 daemon）
you-brain <command>   CLI 命令（与 daemon 通过本地 HTTP API 通信）
Tauri 外壳            菜单栏 + WebView；启动时确保 daemon 在运行
```

- 同一台设备只允许一个 daemon（通过锁文件保证）。
- **开机自启**：桌面端由 Tauri autostart 插件拉起外壳，再由外壳拉起 daemon（已实现）。服务器模式由 `you-brain service install [--no-start] [--print]` / `uninstall` / `status` 生成并管理 launchd 与 systemd 用户单元（`packages/cli/src/service/`）；`you-brain uninstall` 先停服务再清理。真实 `launchctl` / `systemctl` 与无界面机器上的 Drive 登录未验证。前台运行仍可用 `you-brain daemon`。

### 14.2 本地 HTTP API

- 只监听 `127.0.0.1`，端口写入数据目录中的 `daemon.json`；每个请求都必须携带启动时生成的随机 token（同样存放在 `daemon.json`，文件权限 600）。
- 服务器上远程打开 Web UI 时，通过 SSH 隧道或 Tailscale 转发端口，不直接对外监听。
- 主要接口（`packages/core/src/http/handlers.ts`；SSE 在 `http/server.ts` 里提前返回）：`GET /api/today`；`GET /api/topics`（查询参数 `zone`、`status`）；`GET /api/topics/:id` 与 `POST /api/topics/:id`（body 的 `op` 为 `rename`、`status`、`merge`、`split`）；`GET /api/portrait`、`GET /api/portrait/snapshots`；`GET /api/search`、`GET /api/devices`、`GET /api/status`；`GET` 与 `PUT` 的 `/api/roles`、`/api/config`；`GET /api/reminders`（固定 `{ reminders: [] }`）；`POST /api/actions/sync`、`/api/actions/upload`、`/api/actions/todo`、`/api/actions/conclusion`；SSE 为 `GET /api/events`。

## 16. 接管 BrainHub

`setup` 时执行：

1. **检测**：BrainHub 的配置文件（`~/Library/Application Support/brainhub-mcp/` 或 XDG 路径）、launchd plist 或 systemd timer、各客户端 MCP 配置中的 `brainhub` 条目。
2. **展示**：列出将要停用的项目，询问用户。
3. **停用**：卸载 BrainHub 的定时任务（保留单元文件的备份）；从各客户端 MCP 配置中移除 brainhub 条目（保留备份）；不删除 BrainHub 本身及其本地数据。
4. **继承**：读取 BrainHub 的 Drive 根目录和设备 ID 作为默认值，使 `inbox/<device>/` 路径保持连续。
5. **恢复**：`you-brain brainhub restore` 从备份中还原以上配置。

## 17. 安全

- 传输全程 HTTPS（Google API）。
- 密钥（OAuth refresh token、模型 API Key）只存放在系统钥匙串中，绝不写入文件、日志或 Drive。
- 默认开启凭证脱敏，沿用 BrainHub `capture/redact.ts`。
- 本地 HTTP API 只监听回环地址，并使用 token 鉴权。
- 无遥测。

## 18. 风险与 M0 验证项

这些事项的验证脚本在 `scripts/m0/`，结论见[进度.md](./进度.md)的 M0 表：1、2、6 在本机运行过（部分通过 / 通过 / 部分通过），3、5 需真实 Drive，4 需真实 CLI 额度，脚本已备未运行。

| # | 验证项 | 失败时的备选 |
|---|---|---|
| 1 | `@huggingface/transformers`（onnxruntime）能否在 Bun 及其编译产物中运行 | 搜索模块以 Node 子进程运行；或第一版只做 FTS5 关键词搜索 |
| 2 | `sharp` 在 `bun build --compile` 产物中能否运行 | 改用 WebAssembly 版图片处理库，或由 Tauri 端处理 |
| 3 | Drive `files.update` 原地更新在并发场景下的 etag 行为 | 退回为单设备串行上传加重试 |
| 4 | 各 CLI 恢复会话时的 ID 行为（Claude Code、Codex、Grok、Gemini、Cursor） | 在适配器中按内容前缀判断延续关系 |
| 5 | Drive `changes.list` 在 60 秒轮询下的配额与延迟 | 拉长轮询间隔，在 GUI 打开时提高频率 |
| 6 | Tauri 外壳与 Bun daemon 的打包、签名、开机自启流程 | 由 Tauri sidecar 管理 daemon |

其他已知风险：

- **Drive 无追加写**：事件按天分片，单日文件较小，原地更新的成本可控。
- **测试模式 7 天重新登录**：在提交受限范围审核之前，这是体验上的已知代价。
- **模型输出不稳定**：用 zod 校验，失败时重试一次，仍然失败则跳过本次提炼并记录，等下次空闲再试。

## 19. 测试策略

- 沿用 BrainHub 的 `memory-drive` 内存实现，模拟 Drive 做单元测试和集成测试。
- 事件合并：对随机打乱顺序、重复投递的事件流做属性测试，验证各设备合并结果一致。
- 适配器：每个来源准备真实 transcript 样例（脱敏后）作为测试夹具。
- 提炼：用固定的模型响应做快照测试；另外提供一个可选的真实模型冒烟测试。
- 多设备：在同一台机器上启动两个使用不同数据目录的 daemon，连接同一个测试 Drive 根目录，做端到端验证。
