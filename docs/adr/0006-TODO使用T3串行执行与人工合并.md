# ADR-0006：TODO 使用 T3 串行执行与人工合并

状态：已接受（2026-11-16）；2026-11-17 起适配 T3 0.1.9（第 4、7 条及使用前提已更新）；2026-11-20 起项目内改为并行执行、合并逐个进行（第 2、6 条及使用前提已更新，标题中的“串行”现仅指合并）；2026-11-22 起确认合并后自动同步 develop、推送并清理（第 6、7、9 条及使用前提已更新，原“不 push、不删除”“同步后回 T3 检查并重新核对”已取消）。

## 背景

用户需要把开发 TODO 关联项目，自动处理其中优先级最高的一项，并在人工核对、合并到 `develop` 后继续下一项。执行入口确定为 T3，任务队列及人工合并入口由 U-Brain 提供。

## 决定

1. **独立的开发 TODO**：`/todos` 支持标题、说明、P0–P3 优先级和可选项目。项目来自本机 T3；项目默认暂停，由用户开启自动领取。用户也可以手动启动指定 TODO，不改变项目自动领取开关。未关联项目的 TODO 仅能手动在本机用户主目录新开 T3 会话，不参与 Git 核对和合并。T3 若未登记该目录，仅登记已有文件夹，不新建目录或初始化仓库。
2. **项目内并行执行、逐个合并**：P0 最高，同优先级按入队顺序。每个任务有独立分支和工作树，同一仓库最多 3 项同时处于准备、需求确认、执行或合并中；待核对和执行后失败的任务不占名额。尚未派发成功就失败的任务仍占名额，避免 T3、模型或 Git 配置问题让整个队列连续失败。暂停只影响后续领取，不取消当前任务。（2026-11-20 前为严格串行：待核对和失败也阻塞下一项，项目在等人核对时空转。）
3. **任务隔离**：从已有的本地 `develop` 创建 `task/<任务编号>` 及独立 Git worktree。保留所有权记录，恢复时核对仓库、分支及路径；不覆盖其他工作树或用户未提交修改。
4. **T3 负责执行**：适配 T3 0.1.9 对外的 MCP 接口（`/mcp`）。T3 0.1.9 已移除 HTTP 派发接口，会话读写改用 `t3_project_list`、`t3_thread_list`、`t3_thread_launch`（`existing_worktree` 绑定任务工作树）、`t3_thread_read`、`t3_thread_send`。凭据由本机 `t3 auth pairing create` 签发一次性配对码，经 T3 的 MCP OAuth（PKCE）换取访问令牌，上限为 `full-access`，以便沿用用户在 T3 选的权限；令牌仅保存在内存，daemon 退出时按标签撤销，启动时撤销上次异常退出遗留的同名凭据。使用项目默认模型或最近会话的有效模型；权限沿用项目最近会话，无历史配置时用 `auto`。已有任务恢复和返工沿用该会话当前权限。T3 仍可依其权限模式请求批准。
5. **人工核对具体提交**：T3 必须完成最新一轮、结束输出，并在任务分支提交相关变更，才能进入核对。核对页提供摘要、提交 SHA、文件统计及有界 diff；从任务与 `develop` 的共同祖先对比，但不早于任务起点。`develop` 有独立提交不阻止核对，也不计入任务差异。长 diff 显示截断提示。确认请求必须携带核对过的 SHA，提交变化后必须重新核对。退回在原会话和原工作树继续处理。
6. **确认后一步到位：同步、快进、推送、清理**：确认后才开始。并行任务先合并后，任务分支会落后于 `develop`：此时在任务工作树中把本地 `develop` 普通合并进任务分支（不 rebase），以合并提交为准继续快进，不再回 T3 检查、不再要求重新核对；`develop` 又被其他任务推进时最多再同步 2 次，仍追不上则保留待核对状态。有冲突时撤销自动合并、恢复到核对版本，由 T3 在原会话中合并并解决冲突，完成后重新进入人工核对。快进本地 `develop` 成功后，自动把 `develop` 推到远端（只推这一个分支，不强推；远端取 `branch.develop.remote`，缺省 `origin`，没有该远端就跳过推送），然后删除任务工作树和任务分支（只删已完整合入 `develop`、工作树干净的），并从列表移除这个 TODO。`develop` 退回到任务起点之前等其他分歧仍保留待核对状态，提示人工处理。目标分支已检出时要求工作区干净；未检出时用旧值比较更新 ref。分歧、未提交内容或任务分支改变均保留现场。自动流程仍不部署。自动合入的结果没有再经人工核对和测试，这是为了让并行任务一次确认走完；风险由任务之间的实际冲突面决定，冲突本身仍交给人。
7. **持久化与恢复**：状态在数据目录的 `tasks/board.json` 原子保存，不随 Drive 同步。先记录派发编号再派发，会话编号由 T3 分配、派发成功后写入。T3 只在同一 MCP 凭据内按 `clientRequestId` 去重，daemon 重启会换凭据，因此重新派发前先按任务标题和任务工作树找回已建会话；返工前若最后一条用户消息已是同一说明且未失败，视为已投递。人工批准的 SHA 先保存再合并；快进成功后立即记下 `merged`，之后推送失败、清理失败或崩溃，都只补做推送、清理和移除，不再重复合并。推送失败（远端领先被拒绝、网络或认证问题等）时任务保持“失败”并显示 Git 的原因，轮询不会自动反复推送，人工处理后点“重试”再推。Git 已成功而状态保存失败时，恢复只补记同一批准版本，不另领任务。项目目录变化自动暂停并拒绝操作原任务。
8. **手动启动先确认需求**：对指定 TODO 点「开始」时，以 T3 计划模式打开会话，首轮只读了解需求、确认验收口径并提出计划；等待用户在 T3 确认后继续执行。计划阶段仍占用关联项目的串行位置，不进入代码核对。主目录会话重试时用首条消息里的派发编号区分同名 TODO；自动领取行为不变。
9. **识别外部合并**：T3 完成后，任务分支若有新提交且当前提交已包含在本地 `develop` 中，视为已合并，不重复合并，同样推送 `develop`、清理分支和工作树并移除任务。此前因此误报的任务也可在轮询时恢复；停在任务起点的分支仍等待提交。仅凭远端状态或代码内容相同不补记完成。
10. **手动完成**：用户可把未完成且不在合并中的任务标为「已完成」，无需连接 T3，不合并代码或停止原会话，也不触碰分支和工作树。手动完成会释放该任务在队列中的位置；开启自动处理的项目可继续领取下一项。
11. **任务图片**：可在任务说明中粘贴图片，也可选取本地图片。最多 4 张，每张最多 10 MB。图片保存在本机数据目录的 `tasks/images/`，不放进工作树或 Drive；在任务首次派发时以原生附件随首条消息发送给支持附件上传的 T3。列表和核对里的「在 T3 中打开」进入指挥台的同一个 T3 会话。
12. **跨项目任务**：新建、编辑或导入纪要时可勾选多个已有 T3 项目，指定一个主项目；同一个 Git 仓库不可重复选。主项目负责自动领取，每个关联仓库都计入并行上限。先准备好每个仓库的任务分支和工作树，再只在主项目开一个 T3 会话，提供其余工作树的绝对路径和分支。会话须在当前权限下检查这些目录可用；若不能访问，提示用户处理，不自动扩大权限。
13. **跨项目核对与续交付**：逐仓展示差异，一次人工确认锁定待交付的整批提交。无改动的仓库跳过合并和推送；若同步 `develop` 改变已核对的提交，即使没有冲突也要重新核对，冲突仅交回原会话处理对应工作树。分别记录各仓合并、推送、清理进度；部分失败后只继续未完成的步骤，不回滚已交付仓库。逐仓核对在设备的 Web TODO 页面完成；旧手机端不能批准多仓任务。

## 使用前提与异常处理

- 本机 T3 运行中，`t3 auth pairing create` 可用；连接地址沿用指挥台的 T3 设置。
- 关联项目需指向 Git 仓库根目录且已有本地 `develop`。自动领取需要配置项目模型或已有会话；手动启动没有可继承的项目模型时使用 T3 自身的默认模型。U-Brain 不自动创建基线分支或选择未知模型。
- 启动自动处理后，在 TODO 的“核对变更”中检查结果和测试；勾选已核对，再确认合并。合并成功后自动推送 `develop`、清理任务分支和工作树并移除该 TODO；保持开启的项目继续领取，队列清空后等待新任务。推送需要本机 Git 已配置好免交互的远端认证（SSH 密钥或凭据助手），否则按失败处理。
- T3 连接失败保留队列；离线时仍可暂停领取。任务失败后可打开 T3 检查，完成修复或重试，再重新核对。
- 确认合并时任务分支未包含最新 `develop`，会自动合入并继续合并（见第 6 条）；有冲突才交回 T3，完成后重新核对再确认。其他任务执行或核对错误处理后用“重试 / 重新检查”。自动流程不做 rebase、冲突解决或丢弃改动。
- 自动检查拒绝环境配置、凭据与密钥文件的变更；核对正文读取前即检查路径。人工仍需检查代码和验收结果，自动状态不能代替验收。

## 验证边界

回归测试覆盖队列、重启恢复、异常保存、HTTP 入口，以及真实临时 Git 仓库中的完整领取、核对和合并链路。T3 派发由模拟 MCP 服务验证。2026-11-17 在本机 T3 0.1.9 上用真实模型跑通：配对授权、项目列表、派发到临时工作树、同编号重复派发与换编号后找回同一会话、完成判定、返工投递与重复返工去重、退出撤销凭据。
