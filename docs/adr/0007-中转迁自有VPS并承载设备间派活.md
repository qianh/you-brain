# ADR-0007：中转迁自有 VPS，并承载设备间派活

状态：已接受（2026-11-22），实施中。代码侧（Bun 版中转、设备凭据、指令协议、目标端执行器、发起端与 MCP 工具、指挥台多端点）按 [跨设备派活-实施计划](../跨设备派活-实施计划.md) 推进；VPS 上线、真机联调和 Cloudflare 下线等需要真实环境的步骤见该计划的 M0、M1 切换步骤与 M7，完成后把状态改为已实施。

## 背景

Telegram 中转原先跑在 Cloudflare Workers 上，只转发提醒和手机回复。现在要让任一设备（VPS 上的主控 Agent 或另一台 Mac）把任务派到另一台设备的 T3，结果回到发起方并可推到手机。T3 link 过渡方案要为每台设备配 Tunnel、Access、配对和续期脚本，设备一多就撑不住。

## 决定

1. **中转迁到自有 VPS**：Bun 服务 + systemd + Caddy 反代，监听 `127.0.0.1`；`core.ts` 与运行时无关，只换外壳。设备只主动连出一条 WebSocket。daemon 仍不监听 `0.0.0.0`（`部署.md` §6.6 的红线不变）。
2. **主控 Agent 先放在 VPS 的 T3 里**：T3 会话可直接用 `you-brain mcp`，不依赖 dsh 在服务器上跑通。
3. **派活目标仅 T3**：项目列表、开会话、发消息、读结果，复用 `T3Automation`；不改 T3，不读写 T3 数据库；第一期不派给 tty7 会话和 dsh 子代理。
4. **权限取上限**：实际权限 = min(请求值, 目标设备本机上限)，上限默认 `auto`；`full-access` 要在目标设备上手动开；`approval-required` 不作为可选档（手机派活会卡在审批上）。
5. **凭据**：每设备独立令牌 + 一次性邀请码入网，令牌只存哈希，可单台吊销；指令由发起设备的 Ed25519 密钥签名，目标设备用**本机确认过的公钥**验签，不信中转转来的公钥；目标设备本机策略决定「允许哪些设备、哪些项目派活」。三层（中转鉴权、指令签名、目标端白名单）各自独立验证，中转被攻破不能凭空伪造指令。
6. **界面接入**：先做多端点 + 隧道映射到本机回环，`normalizeT3Url` 只接受回环的约束不变；本机 T3 地址（`you-brain.deck.t3-url`）仍代表本机，额外端点另存；每个转发用 Cookie 名前缀隔离，避免同一回环主机上的多个 T3 互相覆盖登录。中转承载 T3 界面流量只作为后手，视隧道方案的使用情况再定。
7. **不排队**：目标离线时指令立即失败，避免设备上线后补执行过期指令；指令 TTL 60 秒，带 `ts` 与 `nonce` 防重放；幂等由目标端账本（指令 ID → 会话）保证，因为 T3 只在同一 MCP 凭据内按 `clientRequestId` 去重。

协议与数据结构见 [跨设备派活-协议](../跨设备派活-协议.md)。

## 后果

- VPS 成为单点：中转挂了，推送和派活都中断。应对：systemd `Restart=always`、设备端指数退避重连、`/check` 监控；T3 link 过渡方案在派活稳定运行前不拆。
- 回滚：`ensureWebhook` 改为先 `getWebhookInfo` 比对再注册，设备改回 Cloudflare 地址后 webhook 会自动改回；Cloudflare Worker 保留一周后再下线，且其中的旧 `ensureWebhook` 需重新部署一次才有同样的回滚能力。
- 过渡期中转同时接受旧共享密钥，但用旧密钥连上的设备不能收发派活指令；全部设备入网后关闭（`RELAY_ACCEPT_LEGACY_KEY=false`）。
- 升级后本机 T3 在指挥台内需要重新登录一次（Cookie 名带了前缀）。
- T3 升级改动 MCP 行为时执行器可能失效：执行器只用 `T3Automation` 已适配的接口，不兼容时拒绝派活并提示。
