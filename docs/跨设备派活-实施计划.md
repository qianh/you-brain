# 跨设备派活：实施计划

> 建立：2026-11-21 ｜ 状态：**M0～M6 已实施并联调（2026-11-22，VPS 中转已上线、Telegram 已切换）；M7 待观察一周后收尾，MacBook Air 待入网**
> 依据：[跨设备派活.md](./跨设备派活.md)（调研与 T3 link 过渡方案）、`services/telegram-relay`、`packages/core/src/deck/t3/*`、ADR-0006。
> 对应 TODO：K0、K1（见 `docs/TODO.md` K 节）。
> 命名沿用 `CONTEXT.md`：本能力叫**跨设备派活**，不叫调度。

## 1. 目标与范围

**目标**

1. 中转从 Cloudflare 迁到自有 VPS，设备只需主动连出，不再为每台设备配 Tunnel、Access、配对和续期脚本。
2. 任一设备（VPS 上的主控 Agent 或另一台 Mac）可以把任务派到另一台设备的 T3，结果回到发起方，并可推到 Telegram。
3. 两台 Mac 的桌面端可以在指挥台里切换查看其他设备的 T3。

**不做**

- 不让 daemon 监听 0.0.0.0（`部署.md` §6.6 的红线不变）。
- 第一期不派给 tty7 会话、dsh 子代理；不做 Windows、手机端。
- 不改 T3 本身，不读写 T3 数据库。

## 2. 关键决定（回应 `跨设备派活.md` §4 的待决定项）

| 事项 | 决定 | 理由 |
|---|---|---|
| 主控 Agent 在哪 | **先放 VPS 的 T3 里** | 已在用，T3 会话能直接用 `you-brain mcp`（`clients/auto-install.ts` 会把它写进 claude / codex 等配置），不依赖 dsh 在服务器上跑通。dsh 作为后期可选 |
| 派活目标 | **仅 T3**（项目列表、开会话、发消息、读结果） | `T3Automation` 已有 `projects` / `start` / `followup` / `sendMessage` / `inspect` / `latestAnswer` / `threadStates`，不用新写 T3 对接 |
| 默认权限 | 目标设备本机设**上限**，默认 `auto`；`full-access` 要在该设备上手动开 | 实际权限 = min(请求值, 设备上限)；`approval-required` 会让手机派活卡在审批上，不作为可选档 |
| 凭据 | **每设备独立令牌 + 一次性邀请码入网**；指令带发起设备签名，目标设备本地确认"允许哪些设备派活" | 中转被攻破时不能凭空伪造指令；沿用单一共享密钥无法吊销单台设备 |
| 界面接入 | **先做多端点 + 隧道映射到本机回环**；中转承载 T3 界面流量作为可选后手 | 保持 `normalizeT3Url` 只接受回环的安全约束；工作量小一个量级 |
| 中转部署 | VPS 上 Bun 服务 + systemd + Caddy 反代（域名已有） | `core.ts` 与运行时无关，只需换外壳 |

## 3. 架构

```
手机 ── Telegram / VPS 的 T3 网页
          │
VPS ── T3（主控 Agent）──you-brain mcp──> VPS daemon ──┐
          │                                            │ 出站 WSS
          └── relay（Bun，监听 127.0.0.1，Caddy 做 HTTPS）<┘
                    ▲                ▲
              出站 WSS          出站 WSS
                    │                │
              Mac A daemon      Mac B daemon
                    │                │
              本机 T3 MCP        本机 T3 MCP
```

- 指令路径：发起设备签名 → relay 校验入网身份并转发 → 目标 daemon 验签、查本机策略 → 调**本机** T3（沿用现有 `t3 auth pairing create` 换令牌的逻辑）→ 结果沿原路回。
- relay 只转发和记录元数据，不持有任何 T3 令牌。

## 4. 里程碑

总体约 **13～16 个工作日**。M1 → M2 → M3 → M4 → M5 顺序做；M6 与 M1～M5 无依赖，可并行；M7 最后。

### M0 前置核对（0.5 天）

- 核对 K0：`部署.md` §11 已记录 VPS 在 2026-11-21 跑通一轮，但 `TODO.md` D4 仍未勾。补做"每日 03:00 沉淀真实执行一次"，并更新两处文档的口径。
- 确认 VPS：域名与 Caddy（或其他 HTTPS 反代）、从 VPS 能连 `api.telegram.org`、两台 Mac 到 VPS 的往返延迟（`curl -w` 测几次）。
- 写 ADR-0007：中转迁自有 VPS，并承载设备间指令；记录第 2 节的决定。

**验收**：D4、K0 状态与文档一致；ADR 评审通过。

### M1 中转 Bun 版，只迁 Telegram（约 2 天）

**改动**

- `services/telegram-relay/src/server.ts`（新）：`Bun.serve` + WebSocket，复用 `core.ts` 不改逻辑。
  - 存储：JSON 文件 + 临时文件原子替换，权限 0600。
  - **并发**：`core.ts` 里 `devices` / `routes` 是读—改—写，Durable Object 天然串行，Bun 里不是。外壳加一个按 relay 实例串行的队列，`frame()`、`update()`、`connected()` 都进队列。
  - 心跳：收到文本 `ping` 直接回 `pong`；同设备重连踢旧连接，关闭码 4000。
  - webhook secret、`/check`、`/connect` 校验与 `worker.ts` 保持一致。
- `core.ts` 的 `ensureWebhook`：缓存标记改为**先 `getWebhookInfo` 比对当前 URL**。否则回滚到 CF 时，CF 仍记着"已设置"，不会重新注册 webhook，Telegram 收不到消息。
- 部署：systemd 单元（密钥放 0600 的环境文件，不经聊天、命令行参数、日志）、Caddy 站点配置、`README` 新增 VPS 部署一节。
- 测试：`core` 已有用例照跑；新增 server 层集成测试（两台模拟设备、重连踢旧连接、并发 `send` 不丢路由）。

**切换步骤**（可回滚）

1. VPS 上起新中转，先不动设备。
2. 一台 Mac 切到新地址：中转自动 `setWebhook` 到 VPS。Telegram 绑定存在中转里，需要在新中转重新绑定一次。
3. 另一台 Mac 和 VPS daemon 切过去；各发一条测试消息，验证推送和回复路由。
4. 保留 CF Worker 一周不删。回滚 = 设备改回 CF 地址（有了 `getWebhookInfo` 比对后 webhook 会自动改回）。

**验收**（按层单独验证）

- relay 层：两台设备在线，`/devices` 可见。
- Telegram 层：推送到手机，回复被推送设备收到；回复另一台设备的提醒路由正确。
- 异常：重启 relay 后设备自动重连；VPS 上 `kill -9` 后 systemd 拉起。

### M2 设备凭据与入网（约 2 天）

**改动**

- relay 新增设备表：`{deviceId, name, tokenHash, publicKey, createdAt, revokedAt}`。
- 入网：VPS 上执行 `relay invite` 生成 10 分钟有效的一次性邀请码；设备兑换后拿到专属令牌，存钥匙串（沿用 `relayKey` 的 `SecretStore`），并上报自己的 Ed25519 公钥。吊销命令 `relay revoke <设备>` 立即断开该设备并拒绝重连。
- 管理密钥与设备令牌分开：`RELAY_KEY` 只保留给 webhook 校验和管理操作。
- `TelegramRelayClient` 的鉴权头改用设备令牌；设置页"连接信息"改为"邀请码"（`invite.ts` 扩展）。过渡期 relay 同时接受旧共享密钥，M2 验收后关闭。
- 审计：relay 追加写 `audit.jsonl`（时间、发起设备、目标设备、动作类型、结果，不含正文）。

**验收**：邀请码一次性、过期、错误 5 次作废（参照现有绑定码逻辑）；被吊销设备无法重连；旧共享密钥关闭后设备仍正常。

### M3 设备间指令协议（约 2 天）

**帧**（在现有 `req` / `res` / `state` / `message` 之外新增，旧客户端对未知帧忽略，已核对 `relay.ts #frame`）

- 设备 → 中转：`{t:"req", op:"cmd", id, to, cmd:{kind, args}, ts, nonce, sig}`
- 中转 → 目标：`{t:"cmd", id, from, cmd, ts, nonce, sig}`
- 目标 → 中转：`{t:"req", op:"result", cmdId, ok, result|error}`，由中转转回发起方
- 事件推送：`{t:"event", from, dispatchId, kind, data}`（会话状态变化）
- 设备上报能力：`{op:"hello", version, t3:{ready, version, projects:[{id,name}], agents:[…]}}`，随 `state` 广播给在线设备

**规则**

- 目标离线：中转立即回失败，不排队，避免设备上线后补执行过期指令。
- 指令 TTL 60 秒，`ts` 与 `nonce` 防重放；单条结果上限 256 KB；按设备限速。
- 长任务异步：`launch` 只返回 `threadId`，后续进度走 `event` 或 `read`。
- 版本号：`protocolVersion`，目标不认识的 `kind` 返回明确错误。

**验收**：协议层单元测试（离线、超时、重放、超大结果）；三台模拟设备的集成测试。

### M4 目标端执行器（约 2～3 天）

**改动**

- `packages/core/src/dispatch/`（新）：`DispatchExecutor` 包装本机 `T3Automation`。第一期支持的 `kind`：`t3.projects`、`t3.start`、`t3.followup`、`t3.read`、`t3.threads`。
- 本机策略 `<dataDir>/dispatch/policy.json`：`enabled`（默认关）、`allowedSenders`（设备 ID 与公钥，由本机用户确认后写入）、`allowedProjects`、`maxMode`（默认 `auto`）。
- 验签：用本机确认过的公钥校验，不信 relay 转来的公钥。未允许的发送者、不在白名单的项目一律拒绝并记审计。
- 幂等：ADR-0006 已说明 T3 只在同一 MCP 凭据内按 `clientRequestId` 去重，daemon 重启会换凭据。所以本机维护 `dispatch/ledger.json`（指令 ID → threadId），重试先查账本。
- 通知：收到远程指令时经现有 deck 通知弹一条（谁、派到哪个项目），可在设置里关。
- 事件：复用 `t3/watch.ts` 的 15 秒监视，对"被派活创建的会话"的状态变化发 `event` 帧给发起方。
- 设置页：设备列表里每台设备一个"允许它向本机派活"开关，加项目白名单与权限上限。

**验收**（按层，成功不外推）：策略关闭时全部拒绝 → 开启但不在白名单拒绝 → 白名单内成功创建会话，在本机 T3 界面能看到 → 请求 `full-access` 而上限是 `auto` 时实际为 `auto` → 同一指令重放只建一个会话。

### M5 发起端与主控工具（约 2 天）

**改动**

- daemon：`/api/dispatch/*`（`http/handlers.ts`、`client.ts`、`deps.ts`、`types.ts` 按现有模式）；发起记录存 `<dataDir>/dispatch/outbox.json`。
- `you-brain mcp`（`mcp/server.ts`）新增工具：`list_devices`、`dispatch_to_device`、`get_dispatch_result`、`send_to_dispatch`。
- VPS 上确认 `you-brain mcp` 已写入 VPS 上各 Agent CLI 的配置，并在一个 T3 会话里实测能看到这些工具。
- 结果回到手机：沿用 Telegram 桥，`event` 到达发起方后按现有规则推送（"做完一轮 / 等你处理 / 失败"）。
- 主控提示词：写成 `you-brain-ref` 同类的技能说明，约束"先 `list_devices` 看在线与项目，再派活；不派不在白名单的项目"。

**验收**：手机给 VPS 的 T3 发一句"让 Mac A 在项目 X 里做 Y"→ A 上出现会话 → 完成后手机收到 Telegram 推送，含最后一条回答。

### M6 桌面端接入其他设备 T3（可与 M1～M5 并行，约 3 天）

**M6.0 先做一个 0.5 天的验证（决定后续方案）**

- 在本机用 `ssh -L` 把 VPS 的 T3 映射到 `127.0.0.1:3774`，指挥台地址指过去，观察：能否加载、登录、WebSocket 是否正常。
- **Cookie 冲突**：`proxy.ts` 注释写明 Cookie 不按端口区分。两个 T3 都在 127.0.0.1 上时，同名登录 Cookie 会互相覆盖。用两个端点实测确认现象。

**M6.1 多端点**

- 偏好键 `you-brain.deck.t3-url`（单值）改为端点列表 `[{id, name, url}]` 加当前选中项；兼容旧值（迁移为第一个端点）。`normalizeT3Url` 不变，仍只接受回环。
- 每个端点各起一个 `startT3Proxy`；`preferredProxyPort` 已按上游端口派生，不会撞。
- **Cookie 隔离**（若 M6.0 确认冲突）：转发层给 `Set-Cookie` 的名字加端点前缀、给上游的 `Cookie` 头去前缀，HTTP 与 WebSocket 都处理（`responseHeaders` / `forwardHeaders` 已是集中入口）。
- `deck-t3.tsx` 加设备切换；每个端点单独 `probeT3Web`；切换时保留各端点页面状态（ADR-0004 的既有要求）。
- 隧道怎么建：文档写 `ssh -L` 与 Tailscale 两种；应用内不自动建隧道。

**M6.2（可选，视使用情况再定）中转承载 T3 界面**：把目标 daemon 本机 T3 的 HTTP/WebSocket 多路复用进中转。需要二进制帧、背压、大响应分片，中转会看到 T3 明文，评估 4～6 天。只有当隧道方案用起来不可接受才做。

**验收**：两个端点同时登录互不踢出；切换后输入框草稿保留；删除端点后相关转发进程退出。

### M7 CF 下线与收尾（约 0.5 天，M5 稳定运行一周后）

- 所有设备已在 VPS 中转；`deleteWebhook` 不需要（webhook 已指向 VPS），直接 `wrangler delete`。
- 撤掉 T3 link 过渡方案：各设备 Tunnel 的 `t3-*-link` 路由、CF Access 的 Bypass 策略、`~/.t3-link/relink-*.sh` 与 launchd 任务。
- 文档：`CONTEXT.md` 指挥台"手机远程"一行里的 Cloudflare 描述、`部署.md` 新增"中转部署"一节、`services/telegram-relay` 重命名为 `services/relay` 并更新 README、`TODO.md` K 节勾选、ADR-0007 状态改为已实施。

## 5. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| VPS 成为单点 | 中转挂了，推送和派活全断 | systemd `Restart=always`；设备端已有指数退避重连；监控 `/check`；T3 link 过渡方案在 M5 稳定前不拆 |
| 中转被攻破 | 若指令只靠中转信任，等于全设备远程执行 | M2 设备令牌 + M3 指令签名 + M4 目标端本地白名单，三层各自独立验证 |
| `full-access` 滥用 | 主控 Agent 被提示注入后在目标 Mac 执行任意命令 | 目标端上限默认 `auto`；项目白名单；审计；通知弹窗可见 |
| Bun 外壳的并发差异 | 路由或设备表被并发写坏 | 串行队列 + 并发集成测试（M1） |
| webhook 回滚失效 | 回滚后 Telegram 收不到消息 | `ensureWebhook` 改为 `getWebhookInfo` 比对（M1） |
| T3 升级改动 MCP 或 Labs 行为 | 目标端执行器失效 | 执行器只用现有 `T3Automation` 的已适配接口；`hello` 上报 T3 版本，不兼容时拒绝派活并提示 |
| 本机 Cookie 冲突 | 多端点互相踢登录 | M6.0 先实测；M6.1 做前缀隔离 |
| VPS 到 Telegram 或到 Mac 的网络质量 | 推送延迟 | M0 实测延迟；超出预期时重新评估是否保留 CF 做 Telegram |

## 6. 验证清单（交付前逐层确认）

1. relay：设备在线、断线重连、重启恢复。
2. 凭据：邀请码一次性、吊销生效。
3. 协议：离线、超时、重放、超大结果。
4. 目标端：策略、白名单、权限上限、幂等，每项单独触发一次。
5. T3：目标 Mac 的 T3 界面里真实出现被派会话，状态变化被回传。
6. 手机：Telegram 收到推送，回复能回到发起会话。
7. 界面：两个远端 T3 同时登录，互不影响。
8. 回滚：M1 切换后能回到 CF；M7 前 T3 link 仍可用。

## 7. 开工顺序建议

1. 先做 M0 和 M1：风险最低，且单独就能把 CF 换掉，立刻看到收益。
2. M6.0 的验证同一天做，它决定界面接入的路线，成本只有半天。
3. M2 → M5 作为一个整体立项，建议到时再用 `/spec` 出规格后拆任务。
