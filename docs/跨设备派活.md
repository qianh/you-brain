# 跨设备派活

> 建立：2026-11-21 ｜ 来源：在 VPS 上部署 T3 Code 并打通「VPS → 其他设备 T3」的过程记录与可行性分析
> 状态：**调研完成，未立项**。现有过渡方案（T3 environment link）已在用，you-brain 内的实现待写规格。
> 命名：`CONTEXT.md`「待定 / 易混」规定「调度」专指每日沉淀，本能力叫**跨设备派活**，不要叫调度。

## 1. 目标场景

在手机上给一台常驻服务器（VPS）下指令，VPS 上的 Agent 判断该交给哪台设备，再把具体任务派到那台设备的 T3 / AI CLI 去执行，结果回到手机。

```
手机（浏览器 / Telegram）
  → VPS（主控：T3 + Agent，判断派给谁）
  → 目标设备（t3-pro、t3-air……）上的 T3 开会话执行
  → 结果回传
```

要求：不依赖 T3 官方客户端和 T3 Connect 中转；所有设备装同一个应用即可加入。

## 2. 现状：已在用的过渡方案（T3 environment link）

### 2.1 部署形态

| 组件 | 位置 | 说明 |
|---|---|---|
| T3 Code 0.1.11 | VPS（Ubuntu 24.04，root）+ 各台 Mac | 官方脚本 `curl -fsSL https://t3.codes/install.sh \| sh` 安装；`t3 service install` 常驻，只监听 `127.0.0.1:3773` |
| Agent CLI | VPS | claude、codex、grok、agy、pi（pi 需要 Node ≥ 22.19，用 NodeSource 装了 Node 22） |
| 浏览器入口 | VPS | cloudflared 远程管理 Tunnel → `t3-<vps>.<域名>` → `http://localhost:3773`，CF Access 只放行本人 |
| link 入口 | 每台被派活设备 | 该设备 Tunnel 再加一条 `t3-<设备>-link.<域名>` → `http://localhost:3773`，CF Access 策略为 **Bypass + IP 范围 = VPS 出口 IP/32** |
| link | VPS | `t3 environment link https://t3-<设备>-link.<域名> --pairing-code <目标设备 t3 pair 的码> --access full-access` |
| 续期兜底 | 目标设备（Mac） | `~/.t3-link/relink-t3-pro.sh` + launchd `com.john.t3-relink-pro`，每天 10:00 及登录时检查，剩余不足 7 天就重新配对并 link |

VPS 上 T3 后台服务的 PATH 不含 `~/.local/bin`，需要在 `~/.t3/service.env` 写 `PATH=...` 后 `t3 service restart`，否则找不到 Agent CLI。

### 2.2 踩过的坑（T3 0.1.11 源码实测）

1. **Linked environments 是 Labs 功能，两端都要开**：设置里 Settings → Labs，或 `~/.t3/userdata/settings.json` 写 `"linkedEnvironmentsEnabled": true`，改完实时生效。只开发起端会报 “Linked environments is off on that machine”。
2. **CF Access 会挡住 link**：link 是服务端到服务端的请求，不带 Access 的登录 cookie，CLI 也没有加自定义请求头的参数，所以不能用 Service Token。
3. **回环地址只给 3 秒探测超时**：`probeTimeout` 对 `localhost` / `127.x` / `::1` 是 3 秒，其他地址 10 秒。最初用「VPS 本机 `cloudflared access tcp` 转发到 127.0.0.1 + Service Token」，跨 CF 一次新连接要 1～3.3 秒，T3 服务端探测频繁超时，判成 unreachable（CLI 的 `environment list` 却显示 reachable，容易误判）。
4. **非回环地址必须 HTTPS**：用解析到 127.0.0.1 的自定义域名绕 3 秒限制时，T3 拒绝：“is plain http, which would send the link's credentials unencrypted”。最终改为直接走 HTTPS 域名 + Access 按 VPS IP 绕过。
5. **同一环境不能挂两个地址**：换地址前要先 `t3 environment unlink <environmentId>`，否则报 “already linked at another address”。
6. **有效期与续期**：link 会话 30 天（`MCP_CLIENT_SESSION_TTL`）。0.1.11 起目标端每次被使用时，若能顺延 ≥ 1 天就重置为「现在 + 30 天」并经响应头 `t3-link-expires-at` 回传（`renewPeerLinkSession`）；0.1.9 没有这段逻辑。30 天内一次没用才会过期。
7. **权限取两者更严**：实际模式 = min(link 的 `--access` 上限, 发起会话自身的模式)。档位：`read-only`、`approval-required`、`auto-accept-edits`、`auto`、`full-access`。`approval-required` 下审批要在目标设备的 T3 里点，手机派活会卡住。
8. **MCP 不用装**：T3 服务端自带 `/mcp`，会以 `t3-code` 名义自动注入 Claude、Codex 等 Agent 会话；link 后 Agent 用同一组编排工具带上目标 `environmentId` 即可在对方开会话、发消息。

### 2.3 过渡方案的局限

- 每加一台设备都要：Tunnel 路由、Access 策略、配对、续期脚本，各配一遍。
- 目标设备必须有一个可被访问的 HTTPS 入口。
- 依赖 Labs 功能，T3 升级可能改动行为。
- `full-access` 下，控制 VPS 上的 T3 等于能在目标设备上执行任意命令。

## 3. 在 you-brain 里做：可行性

### 3.1 已有基础

| 能力 | 现状 | 出处 |
|---|---|---|
| 所有设备同一程序、分角色 | 普通设备 / 主设备 / 网页会话处理设备 | `技术方案.md` §1.1 |
| 服务器端 | Linux 安装包 + systemd 常驻，可设主设备；**真实服务器验收（D4）未做** | `部署.md` §6、`TODO.md` D4 |
| 设备注册表 | Drive `devices/<id>.json`，含 `lastActiveAt` | `技术方案.md` §6.1 |
| 调本机 T3 | daemon 经 T3 MCP 调 `t3_thread_list` / `t3_thread_send` | `CONTEXT.md` 指挥台「手机远程」 |
| **跨设备实时通道雏形** | Telegram 中转 `services/telegram-relay`（CF Workers + Durable Objects 免费套餐）：各设备 daemon 主动连出 WebSocket，中转按设备路由 | 同上 |

Drive 同步是异步轮询，不适合派活；Telegram 中转已经是「任意设备 ↔ 指定设备」的实时通道，是本能力的主要复用点。

### 3.2 要补的

1. **控制通道**：中转在 Telegram 消息之外增加设备间指令消息（请求 ID、回执、进度、结果回传、超时）。
2. **目标端执行**：daemon 收到指令后调本机 T3 MCP 开会话 / 发消息，必要时也可派给 tty7 会话；结果回传发起方。
3. **设备能力清单**：注册表补充每台设备的项目、已登录的 Agent、在线状态，供主控选设备。
4. **主控工具**：`you-brain mcp` 增加 `list_devices`、`dispatch_to_device`、`get_dispatch_result` 之类工具，VPS 上的 Agent 直接用；手机入口沿用 Telegram 或 VPS 的 T3 网页。
5. **安全**：中转目前所有设备共用一个密钥，只适合转消息。远程执行至少需要每设备独立凭据、指令签名、可执行范围白名单、审计日志。
6. **前置**：先完成 D4，在 VPS 上把 you-brain 服务器端真实跑起来。

### 3.3 两条路对比

| | T3 environment link（现状） | you-brain 中转派活 |
|---|---|---|
| 新设备加入 | 每台配 Tunnel 路由、Access、配对、续期 | 装应用、登录同一账号，主动连出 |
| 网络要求 | 目标设备要有可访问的 HTTPS 入口 | 只需能连出 |
| 过期 | 30 天会话，靠使用顺延或脚本续期 | 自己设计 |
| 开发量 | 无 | 3.2 的六项 |

结论：设备多了以后走 you-brain 中转；实现之前继续用 T3 link。下一步用 `/spec` 把「跨设备派活」写成规格。
